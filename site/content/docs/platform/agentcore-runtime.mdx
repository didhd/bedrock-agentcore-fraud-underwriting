<Callout type="info" title="Audience">
For the customer's engineer and for anyone writing a client against these endpoints.
Verified against `bedrock-agentcore` **1.14.0** and re-verified on **1.19.0** — see
[the SDK upgrade](/docs/platform/sdk-upgrade). `tests/test_runtime_contract.py` holds
**60 tests** asserting everything on this page.
</Callout>

This port declares two runtimes, both `protocol: HTTP` with one `@app.entrypoint` each:

| Runtime | Path | Shape |
|---|---|---|
| `underwriter` | `app/underwriter/main.py` | Async-generator entrypoint → SSE. Eight-way fan-out, then synthesis, streaming each specialist as it lands. |
| `francis` | `app/francis/main.py` | Interactive router; the eight specialists as `@tool` wrappers under the customer's maximum-2-tools-per-query cap. |

## The `context` parameter must be literally named `context`

<Callout type="error" title="Symptom first">
**What you see.** One of two things, depending on how you wrote the handler.

With a *one-parameter* handler: it runs, but every log line is missing the session id, and
`RequestContext` is nowhere. You spend an afternoon asking why sessions do not stick.

With a *two-parameter* handler whose second parameter is named anything else — `ctx`,
`request_context`, `req` — every request raises `TypeError` at invocation time.

**Cause.** `BedrockAgentCoreApp._takes_context` decides whether to inject the
`RequestContext` by checking that the handler's **second positional parameter is literally
named `context`**. Not by type. Not by annotation. By name.
</Callout>

```python
@app.entrypoint
async def invoke(payload, context):     # `context`, exactly
    session_id = session_id_of(context)
    ...
```

`tests/test_runtime_contract.py::test_second_parameter_is_literally_named_context` asserts
the parameter name on both runtimes, and
`test_sdk_agrees_the_handler_takes_context` asserts that the SDK's own `_takes_context`
returns `True` for it — so the guard is against the SDK's real behaviour rather than
against a restatement of it.

## An async-generator entrypoint returns SSE automatically

Yield plain dicts. Never hand-format SSE.

```python
@app.entrypoint
async def invoke(payload, context):
    yield {"event": "start", "session_id": session_id}
    ...
    yield {"event": "done", ...}
```

The SDK's `_convert_to_sse` serialises each yielded object as `data: <json>\n\n`. The local
`agentcore dev` server and the deployed runtime both reply **`text/event-stream` always** —
even for a one-line prompt. Every client must parse `data: {...}` frames; there is no
"short answers come back as JSON" path.

The batch runtime's frame sequence, asserted by test:

```
start
  agent_start   x8
  agent_done | failure   x8
synthesis_start
done
```

A terminal `error` frame replaces the tail on an unrecoverable failure.

### Choosing sync vs streaming is a resource decision, not a style one

The previous entrypoint here was `def invoke(payload) -> dict`. Three consequences, all
fixed by the async generator:

1. No session id (above).
2. **A Starlette worker held for the whole fan-out.** `_invoke_handler` routes a *sync*
   handler through `run_in_threadpool`, so a tens-of-seconds fan-out occupies a worker
   throughout.
3. Nothing to show until the end — the live UI could not render specialists as they landed.

## Errors arrive AFTER HTTP 200

<Callout type="error" title="This is the one a client will get wrong">
**Symptom.** A monitoring dashboard shows 100% success. Users report failed adjudications.

**Cause.** The response status is committed as **HTTP 200** the moment the first SSE byte
goes out. An exception raised later inside the generator can only be reported *in a frame*.
`_stream_with_error_handling` catches it and yields a terminal
`{"error", "error_type", "message"}` object — after the 200.

**A 200 is not success. Every frame must be inspected for an `error` key.**
</Callout>

This runtime deliberately uses **two different keys** so one client-side check does not
swallow the other:

| Key | Meaning | Terminal? |
|---|---|---|
| `error` | Unrecoverable failure of the whole run. Same shape the SDK itself uses, so one check covers both. | Yes |
| `failure` | A **single specialist** failed. 7-of-8 graceful degradation; the adjudication proceeds with a documented gap. | No |
| `done` | The run completed, possibly partially. Always emitted when it completed. | Yes |

A client that treats any `error`-shaped frame as fatal therefore does not abort on a
degraded-but-valid run. The 42-run benchmark contains a live example: APP-1011 repetition 3
lost `synthetic` and `rings` to `server_5xx`, finished in 21.2 s, and **still validated all
21 keys** (`evals/results/pipeline_14x3_us-east-1.json`).

## Timeouts

| Path | Limit | Adjustable? |
|---|---|---|
| Synchronous request | **15 minutes** | **No** |
| Streaming response | 60 minutes | — |
| Session ceiling | 8 hours | — (this is *not* a request timeout) |

The 8-hour figure appears in enough places to be worth naming explicitly: it is the session
ceiling, not a request timeout. If you have seen "8 hours" quoted as an invocation limit,
that is what it was.

## `runtimeSessionId` has a 33-character client-side minimum

<Callout type="warn" title="Symptom: ParamValidationError on a perfectly good UUID">
`uuid4().hex` is **32** characters and is rejected. `str(uuid.uuid4())` is **36** with the
hyphens and is accepted.

```python
SESSION_ID_MIN_LENGTH = 33

def new_session_id() -> str:
    return str(uuid.uuid4())        # 36, not .hex's 32
```

`app/runtime_support.py` centralises this so nobody re-derives it, and
`test_generated_session_id_meets_the_33_char_floor` asserts *both* halves — that
`uuid4().hex` is below the floor (so the test's premise is checked, not assumed) and that
the generated id clears it.

Also note `RequestContext.session_id` is `Optional[str]` and is `None` whenever the header
is absent, so a fallback is mandatory rather than defensive.
</Callout>

## Only one entrypoint per app

A second `@app.entrypoint` **silently overwrites** the first. There is no error and no
warning. Both runtimes here declare exactly one, and they are separate `codeLocation`
directories precisely so the batch and interactive paths cannot collide.

## The ping handler must reproduce the task check

`@app.ping` is consulted **before** the SDK's automatic behaviour (precedence: forced >
custom > automatic). The SDK's automatic behaviour already reports `HEALTHY_BUSY` while any
tracked async task is open — so a custom handler that does not reproduce that check makes a
long fan-out advertise itself as idle and invites more work onto a busy microVM.

```python
@app.ping
def ping_status() -> PingStatus:
    if app.get_async_task_info()["active_count"] > 0:
        return PingStatus.HEALTHY_BUSY
    return PingStatus.HEALTHY
```

<Callout type="info" title="`@app.async_task` rejects async generators">
`@app.async_task` raises `ValueError: @async_task can only be applied to async functions`
on an async generator — and a streaming entrypoint must be one. So the streaming entrypoint
registers by hand with `app.add_async_task(...)` / `app.complete_async_task(...)` in a
`try/finally`, which keeps the ping status honest for the whole run. The *synthesis* leg,
which is an ordinary coroutine, does use the decorator.
</Callout>

## Keep `debug=False`

```python
app = BedrockAgentCoreApp(debug=False)
```

This is a security decision, not a log-level one. With `debug=True` the SDK routes any
payload carrying `_agent_core_app_action` to `_handle_task_action`, which lets a caller
force the ping status and enumerate running jobs — a health-state backdoor on the
`/invocations` path. `test_debug_mode_is_off` asserts it on both runtimes.

## Payload tolerance is required, because `agentcore invoke` only sends prompts

`agentcore invoke --runtime underwriter "Run a full underwriting review of APP-1004"`
delivers a *prompt*, not a structured payload. So the entrypoint accepts all of these and
extracts the application id from each:

```python
{"application_id": "APP-1004"}
{"prompt": "Run a full underwriting review of APP-1004"}
{"prompt": "check app 1004 please"}
{"prompt": "app_1004"}
{"messages": [{"role": "user", "content": [{"text": "look at APP-1003"}]}]}
```

A payload with no recoverable id yields a structured `error` frame naming the accepted
shapes, not a stack trace.

## Observability: the SDK gives you no token or cost attributes

<Callout type="warn" title="What is and is not instrumented for you">
- Declaring `instrumentation.enableOtel: true` makes AgentCore wrap the entrypoint with
  **`opentelemetry-instrument`**. That wrapper needs `aws-opentelemetry-distro>=0.18.0`
  installed *in the runtime's own `pyproject.toml`* — missing it means the wrapper cannot
  start and the runtime emits **zero spans**, only service-level metrics.
- **The AgentCore SDK emits no token, cost or latency span attributes**, and Strands
  records its token histograms *without* attributes, so they cannot be sliced per agent.
  Per-agent spend telemetry is this repo's own code (namespace `AgentCoreFraudDemo`), which
  is why the runtime execution role carries a namespace-scoped
  `cloudwatch:PutMetricData`.
- Spans require the one-time account-level **CloudWatch Transaction Search** setup, and
  roughly 10 minutes after enabling it before anything is indexed. An empty
  `agentcore traces list` right after the first deploy is expected. See
  [Deployment](/docs/platform/deployment#one-time-cloudwatch-transaction-search).
- **Only Runtime gets a log/trace destination automatically.** Memory and Gateway get none;
  wiring theirs is a manual `PutDeliverySource` → `PutDeliveryDestination` →
  `CreateDelivery` sequence.
- **AgentCore Memory does not work under `agentcore dev`.** The Francis session manager is
  written to no-op when `MEMORY_FRANCISMEMORY_ID` is unset, so local runs are stateless by
  design rather than by accident.
</Callout>

A related fabrication guard worth naming: when a run is offline, token counts and cost do
not exist and are emitted as `null`, all the way to the browser and to CloudWatch — where
the datapoint is **omitted** rather than sent as `0`. A fabricated `0` in a spend metric is
worse than a gap, because a gap is visible and a `0` averages in.
`test_cloudwatch_emission_omits_unmeasured_datapoints_rather_than_sending_zero` asserts it.

## Quotas that matter at the customer's stated volume

<Callout type="error" title="Raise this before any load test, not after">
This is arithmetic on the customer's own aspiration, and it is labelled as such: at
**300,000 applications/day × 9 model calls × ~2,250 tokens ≈ 6.1 billion tokens/day**.
Claude Sonnet 5's daily token ceiling is **8.64 billion and is not adjustable** — that is an
account-team escalation, not a self-serve service-quota ticket.

The volume figure is the customer's, and it is also
[the single unresolved question in the cost case](/docs/cost/snowflake-comparison): nobody
has told us how many applications/day actually go through the full eight-agent forensic
path. At ~3,000/day none of this matters; at 300,000/day it is the first thing to fix.
</Callout>

Two smaller quotas that already shaped code here:

- **Memory `CreateEvent` is throttled per (actor, session) at roughly 5 TPS.** The Francis
  session manager therefore uses `batch_size=5` (`FRANCIS_MEMORY_BATCH_SIZE`) so a
  multi-turn exchange does not walk into it. `test_francis_memory_batch_size_avoids_the_create_event_tps_cap`
  asserts the setting.
- **Throttling was measured at zero on this workload** — `ModelThrottledException` occurred
  **0 times across 336 specialist calls** at concurrency 1
  (`evals/results/tail_analysis.json`). That is a real observation and it is also a narrow
  one: the benchmark ran **one application at a time**, so nothing here says what the
  throttle rate is when N adjudications overlap. Throughput is on the
  [not-measured list](/docs/performance/benchmark-method).

## What this page's figures do and do not cover

<Callout type="warn" title="Runtime overhead is NOT in the measured latency">
The 42-run benchmark called Bedrock **directly from a developer host**, not through a
deployed runtime. Quoted from the artifact's own caveats:

> *"container cold start, session setup and SSE framing are NOT in the end-to-end figures"*

So the 31.45 s p50 (n=42) excludes everything on this page. The repo names this as the
single largest known gap between that figure and what a deployed customer would see. It is
not estimated anywhere.
</Callout>

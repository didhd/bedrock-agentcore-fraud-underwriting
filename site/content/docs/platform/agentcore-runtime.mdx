*For the customer's engineer and for anyone writing a client against these endpoints.*

Four rules govern an AgentCore Runtime entrypoint, and three of them fail silently when broken:
the second parameter must be named `context`, an async generator becomes SSE automatically, an
error raised mid-stream arrives **after** HTTP 200, and only one `@app.entrypoint` survives per
app. Verified against `bedrock-agentcore` **1.14.0** and re-verified on **1.19.0** — see
[SDK upgrade](/docs/platform/sdk-upgrade). `tests/test_runtime_contract.py` holds **60 tests**
asserting everything below.

## Request lifecycle

<Mermaid
  title="Where the 200 is committed, and where an error can still appear"
  chart={`

    R-->>C: data: agent_done
    F-->>R: exception
    R-->>C: data: error, terminal

Step 2 is the whole hazard. Status is committed the moment the first byte of the stream goes
out, so every later failure can only be reported *inside a frame*. A dashboard counting HTTP
status codes reports 100% success on a run that failed.

Two runtimes are declared here, both `protocol: HTTP` with one entrypoint each.

| Runtime | Path | Shape |
|---|---|---|
| `underwriter` | `app/underwriter/main.py` | Async-generator entrypoint → SSE. Eight-way fan-out, then synthesis, streaming each specialist as it lands. |
| `francis` | `app/francis/main.py` | Interactive router; the eight specialists as `@tool` wrappers under the customer's maximum-2-tools-per-query cap. |

## Parameter named `context`, matched by name

Two failure shapes, depending on how the handler was written.

| Handler signature | What happens | Why |
|---|---|---|
| `def invoke(payload)` | Runs, but every log line lacks the session id and `RequestContext` is nowhere | One parameter, so the SDK never injects |
| `def invoke(payload, ctx)` | **Every request raises `TypeError`** at invocation time | Second parameter is not named `context` |
| `def invoke(payload, context)` | Correct | `_takes_context` matches by name |

`BedrockAgentCoreApp._takes_context` decides whether to inject `RequestContext` by checking that
the handler's **second positional parameter is literally named `context`**. Not by type. Not by
annotation. By name.

```python
@app.entrypoint
async def invoke(payload, context):     # `context`, exactly
    session_id = session_id_of(context)
    ...
```

`test_second_parameter_is_literally_named_context` asserts the parameter name on both runtimes,
and `test_sdk_agrees_the_handler_takes_context` asserts the SDK's own `_takes_context` returns
`True` for it — so the guard runs against real SDK behaviour rather than against a restatement
of it.

## Async generator returns SSE automatically

Yield plain dicts. Never hand-format SSE.

```python
@app.entrypoint
async def invoke(payload, context):
    yield {"event": "start", "session_id": session_id}
    ...
    yield {"event": "done", ...}
```

`_convert_to_sse` serialises each yielded object as `data: <json>\n\n`. Local `agentcore dev`
and the deployed runtime both reply **`text/event-stream` always** — even for a one-line prompt.
Every client must parse `data: {...}` frames; there is no "short answers come back as JSON" path.

Frame sequence for the batch runtime, asserted by test:

```
start
  agent_start   x8
  agent_done | failure   x8
synthesis_start
done
```

A terminal `error` frame replaces the tail on an unrecoverable failure.

### Sync versus streaming is a resource decision

The previous entrypoint here was `def invoke(payload) -> dict`. Three consequences, all fixed by
the async generator:

1. No session id, per the table above.
2. **A Starlette worker held for the whole fan-out.** `_invoke_handler` routes a *sync* handler
   through `run_in_threadpool`, so a tens-of-seconds fan-out occupies a worker throughout.
3. Nothing to show until the end — the live UI could not render specialists as they landed.

## Errors arrive after HTTP 200

<Callout type="error" title="A 200 is not success. Every frame must be inspected for an error key">
Symptom pair that identifies this: a monitoring dashboard shows 100% success while users report
failed adjudications. An exception raised inside the generator can only be reported in a frame —
`_stream_with_error_handling` catches it and yields a terminal
`{"error", "error_type", "message"}` object, after the 200 has already gone out.
</Callout>

Three keys, deliberately distinct so one client-side check does not swallow another.

| Key | Meaning | Terminal? |
|---|---|---|
| `error` | Unrecoverable failure of the whole run. Same shape the SDK itself uses, so one check covers both. | Yes |
| `failure` | A **single specialist** failed. 7-of-8 graceful degradation; the adjudication proceeds with a documented gap. | No |
| `done` | Run completed, possibly partially. Always emitted when it completed. | Yes |

A client treating any `error`-shaped frame as fatal therefore does not abort on a
degraded-but-valid run. The benchmark contains a live example: APP-1011 repetition 3 lost
`synthetic` and `rings` to `server_5xx`, finished in **21.215 s**, and still validated all 21
keys (`evals/results/pipeline_14x3_us-east-1.json`).

## Timeouts

| Path | Limit | Adjustable? |
|---|---|---|
| Synchronous request | **15 minutes** | **No** |
| Streaming response | 60 minutes | — |
| Session ceiling | 8 hours | Not a request timeout at all |

That 8-hour figure appears in enough places to be worth naming: it is the session ceiling. If
you have seen "8 hours" quoted as an invocation limit, this is what it was.

## Session id has a 33-character client-side minimum

`uuid4().hex` is **32** characters and is rejected with `ParamValidationError`.
`str(uuid.uuid4())` is **36** with the hyphens and is accepted.

```python
SESSION_ID_MIN_LENGTH = 33

def new_session_id() -> str:
    return str(uuid.uuid4())        # 36, not .hex's 32
```

`app/runtime_support.py` centralises this so nobody re-derives it, and
`test_generated_session_id_meets_the_33_char_floor` asserts *both* halves — that `uuid4().hex`
is below the floor, so the test's premise is checked rather than assumed, and that the generated
id clears it. Note also that `RequestContext.session_id` is `Optional[str]` and is `None`
whenever the header is absent, which makes a fallback mandatory rather than defensive.

## One entrypoint per app

A second `@app.entrypoint` **silently overwrites** the first. No error, no warning. Both
runtimes declare exactly one, in separate `codeLocation` directories precisely so the batch and
interactive paths cannot collide.

## Ping handler must reproduce the task check

`@app.ping` is consulted **before** the SDK's automatic behaviour — precedence is forced >
custom > automatic. Automatic behaviour already reports `HEALTHY_BUSY` while any tracked async
task is open, so a custom handler that omits that check makes a long fan-out advertise itself as
idle and invites more work onto a busy microVM.

```python
@app.ping
def ping_status() -> PingStatus:
    if app.get_async_task_info()["active_count"] > 0:
        return PingStatus.HEALTHY_BUSY
    return PingStatus.HEALTHY
```

One wrinkle: `@app.async_task` raises `ValueError: @async_task can only be applied to async
functions` on an async generator — and a streaming entrypoint must be one. So the streaming
entrypoint registers by hand with `app.add_async_task(...)` / `app.complete_async_task(...)` in
a `try/finally`, keeping ping status honest for the whole run. The synthesis leg, an ordinary
coroutine, does use the decorator.

## Keep `debug=False`

```python
app = BedrockAgentCoreApp(debug=False)
```

Security decision, not a log-level one. With `debug=True` the SDK routes any payload carrying
`_agent_core_app_action` to `_handle_task_action`, which lets a caller force the ping status and
enumerate running jobs — a health-state backdoor on the `/invocations` path.
`test_debug_mode_is_off` asserts it on both runtimes.

## Payload tolerance, because `agentcore invoke` only sends prompts

`agentcore invoke --runtime underwriter "Run a full underwriting review of APP-1004"` delivers a
*prompt*, not a structured payload. So the entrypoint accepts all of these and extracts the
application id from each:

```python
{"application_id": "APP-1004"}
{"prompt": "Run a full underwriting review of APP-1004"}
{"prompt": "check app 1004 please"}
{"prompt": "app_1004"}
{"messages": [{"role": "user", "content": [{"text": "look at APP-1003"}]}]}
```

A payload with no recoverable id yields a structured `error` frame naming the accepted shapes,
not a stack trace.

## Observability: no token or cost attributes come free

| Concern | What AgentCore gives you | What this repo had to add |
|---|---|---|
| Spans at all | Only with `instrumentation.enableOtel: true` **and** `aws-opentelemetry-distro>=0.18.0` in the runtime's own `pyproject.toml`. Missing the dependency means the `opentelemetry-instrument` wrapper cannot start and the runtime emits **zero spans**, service metrics only | the dependency, per runtime |
| Token / cost / latency span attributes | **None.** Strands also records its token histograms *without* attributes, so they cannot be sliced per agent | per-agent spend telemetry in our code, namespace `AgentCoreFraudDemo`, needing namespace-scoped `cloudwatch:PutMetricData` |
| Trace indexing | Requires the one-time account-level CloudWatch Transaction Search setup plus ~10 minutes. An empty `agentcore traces list` right after the first deploy is expected | see [Deployment](/docs/platform/deployment#one-time-cloudwatch-transaction-search) |
| Log and trace destinations | **Runtime only.** Memory and Gateway get none | a manual `PutDeliverySource` → `PutDeliveryDestination` → `CreateDelivery` sequence |
| Memory under `agentcore dev` | **Does not work** | the Francis session manager no-ops when `MEMORY_FRANCISMEMORY_ID` is unset, so local runs are stateless by design |

One fabrication guard belongs beside that table. When a run is offline, token counts and cost do
not exist and are emitted as `null` all the way to the browser and to CloudWatch — where the
datapoint is **omitted** rather than sent as `0`. A fabricated `0` in a spend metric is worse
than a gap, because a gap is visible and a `0` averages in.
`test_cloudwatch_emission_omits_unmeasured_datapoints_rather_than_sending_zero` asserts it.

## Quotas that matter at the customer's stated volume

<Callout type="warn" title="Raise the Sonnet 5 ceiling before any load test, not after">
Arithmetic on the customer's own aspiration, labelled as theirs: **300,000 applications/day × 9
model calls × ~2,250 tokens ≈ 6.1 billion tokens/day**. Claude Sonnet 5's daily token ceiling is
**8.64 billion and is not adjustable** — an account-team escalation, not a self-serve
service-quota ticket.

Nobody has told us how many applications/day actually take the full eight-agent forensic path.
At ~3,000/day none of this matters; at 300,000/day it is the first thing to fix, and it is
[the single unresolved input in the cost case](/docs/cost/snowflake-comparison).
</Callout>

Two smaller quotas already shaped code here:

- **Memory `CreateEvent` throttles per (actor, session) at roughly 5 TPS.** The Francis session
  manager therefore uses `batch_size=5` (`FRANCIS_MEMORY_BATCH_SIZE`), asserted by
  `test_francis_memory_batch_size_avoids_the_create_event_tps_cap`.
- **Throttling measured zero on this workload.** `ModelThrottledException` occurred **0 times
  across 336 specialist calls** (`evals/results/tail_analysis.json`). Real observation, and a
  narrow one: the benchmark ran one application at a time.

## What this page's figures do not cover

**AgentCore Runtime overhead is NOT MEASURED anywhere on this site.** The 42-run benchmark called
Bedrock directly from a developer host rather than through a deployed runtime, and the artifact
says so in its own caveats: container cold start, session setup and SSE framing are not in the
end-to-end figures. So the 31.45 s p50 (n=42) excludes everything on this page, and the repo
names that as the single largest known gap between the measured figure and what a deployed
customer would see. It is not estimated.

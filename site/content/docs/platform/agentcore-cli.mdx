## The trap that cost the most: `configure` and `launch`

**Symptom.** Your CI pipeline runs green. `agentcore configure --entrypoint …` prints
something that looks like help text, `agentcore launch` prints something similar, the shell
reports exit 0, the job goes green — and no AWS resource was created, updated, or even
contacted. You discover it when someone tries to invoke a runtime that does not exist.

**Cause.** There are two different programs named `agentcore` on a typical developer
machine, and only one of them is the real CLI.

<Tabs items={['The npm CLI (real)', 'The pip starter toolkit (deprecated)']}>
<Tab value="The npm CLI (real)">

`@aws/agentcore` has no `configure` and no `launch` verb. It rejects both:

```console
$ agentcore configure --entrypoint agentcore_runtime.py
error: unknown command 'configure'
(Did you mean config?)
$ echo $?
1
```

That is the *safe* failure. Exit 1 stops a `set -e` script.

</Tab>
<Tab value="The pip starter toolkit (deprecated)">

`bedrock-agentcore-starter-toolkit` installs a console script **also named `agentcore`**.
On that binary `configure` and `launch` *parse* — and then do approximately nothing useful
for this project. Whichever binary resolves first on `PATH` decides which tool your CI
actually invoked. A pipeline built on those verbs can report success while deploying zero
infrastructure.

This is why `requirements.txt` lists the package under a heading reading
**DELIBERATELY ABSENT** rather than simply omitting it.

</Tab>
</Tabs>

<Callout type="error" title="Both halves of this are guarded in CI">
`deploy/ci.sh` step 0 does two things before anything else runs:

1. greps every tracked-or-untracked-but-not-ignored file for the literal strings
   `agentcore configure` and `agentcore launch`, and fails the build if either appears
   (with four documented exemptions — the files whose purpose is to warn about them);
2. fails if `bedrock-agentcore-starter-toolkit` is installed at all, because with it on
   `PATH` every subsequent `agentcore` call in the script is ambiguous.

The guard exists because *this repository shipped with that failure*. The earlier
`deploy/deploy.md` instructed two commands that do not exist.
</Callout>

## The real verb set

```
create   add      remove   validate   package   deploy
dev      invoke   logs     traces     status
fetch    exec     import   run
```

The flow that actually deploys this project:

<Steps>

<Step>
**Install the toolchain, and remove the collider.**

```bash
npm install -g @aws/agentcore      # requires Node >= 20
agentcore --version                # expect 1.0.0-preview.22
pip uninstall -y bedrock-agentcore-starter-toolkit
```

Telemetry is **on by default** — relevant for a regulated customer. Opt out per machine
with `agentcore config telemetry.enabled false`, then confirm with
`agentcore telemetry status`.
</Step>

<Step>
**Install the CDK app's dependencies. This is not optional.**

```bash
(cd agentcore/cdk && npm install)
```

*Symptom if you skip it:* `agentcore deploy` dies in the TypeScript build with

```console
tsconfig.json(5,25): error TS5107: Option 'moduleResolution=node10' is deprecated
and will stop functioning in TypeScript 7.0.
```

*Cause:* `agentcore deploy` runs `npm run build` (bare `tsc`) inside `agentcore/cdk/`. The
vended project pins `typescript: ~5.9.3` as a devDependency. With no local install, `tsc`
resolves to whatever is global and the vended `tsconfig.json` fails under a newer compiler.
Install the pinned compiler; do **not** edit the vended tsconfig.
</Step>

<Step>
**Validate.**

```bash
agentcore validate --json --directory "$REPO_ROOT"
```

Non-interactive and machine-readable. Exits 1 with `{"success":false,…}` on any Zod
failure. This creates nothing and needs no credentials.
</Step>

<Step>
**Package, then dry-run.**

```bash
agentcore package                        # writes agentcore/<runtime>.zip
agentcore deploy --dry-run --target default --json
```

It is `--dry-run`, **not** `--plan`. The AWS docs' `--plan` flag does not exist here:
`error: unknown option '--plan'`. (Internally the CLI maps `--dry-run` onto a `plan`
option, which is probably where the docs bug came from.) `--dry-run` returns after the
deployability check and before `deployStack`, so it synthesizes CloudFormation and touches
nothing.
</Step>

<Step>
**Deploy.**

```bash
agentcore deploy --target default --yes
```
</Step>

</Steps>

## Project layout, and what the config demands of the code

This repo's `agentcore/` directory is hand-authored and `agentcore validate` passes on it.
It declares two runtimes and one memory.

<Files>
  <Folder name="agentcore" defaultOpen>
    <File name="agentcore.json" />
    <File name="aws-targets.json" />
    <Folder name=".cli">
      <File name="deployed-state.json" />
    </Folder>
    <Folder name="cdk">
      <File name="package.json" />
      <Folder name="bin"><File name="cdk.ts" /></Folder>
      <Folder name="lib"><File name="cdk-stack.ts" /></Folder>
      <Folder name="test"><File name="cdk.test.ts" /></Folder>
    </Folder>
  </Folder>
</Files>

| Declared in `agentcore.json` | What `app/` must supply |
|---|---|
| `codeLocation: app/underwriter/`, `entrypoint: main.py` | `app/underwriter/main.py` **and** `app/underwriter/pyproject.toml`. `agentcore package` fails with `Required project file not found: …/pyproject.toml` without the latter — the config alone is not enough. |
| Same for `app/francis/` | Same two files. |
| `runtimeVersion: PYTHON_3_12` | `requires-python = ">=3.12"` in each `pyproject.toml`. |
| `instrumentation.enableOtel: true` | `aws-opentelemetry-distro>=0.18.0` in **each** `pyproject.toml`, not only in `requirements.txt` — `agentcore package` builds each runtime's closure from its own pyproject. |
| `protocol: HTTP` | An `@app.entrypoint` whose second parameter is literally named `context`. See [AgentCore Runtime](/docs/platform/agentcore-runtime). |
| `memories[].name: francisMemory` | Deploy injects the id as **`MEMORY_FRANCISMEMORY_ID`** (the name upper-cased). The session manager must read exactly that name, and no-op when unset so `agentcore dev` still works. |

### Naming constraints the schema enforces

All four are checked by `agentcore validate` before any AWS call, and they are not
consistent with each other:

| Thing | Pattern | Note |
|---|---|---|
| Project name | `^[A-Za-z][A-Za-z0-9]{0,22}$` | Alphanumeric only, max 23. No hyphens, no underscores. `ppFraud` is 7. |
| Runtime / memory name | `^[a-zA-Z][a-zA-Z0-9_]{0,47}$` | Underscores allowed, **hyphens are not**. `under-writer` fails. |
| Deployed runtime name | `<project>_<runtime>`, ≤ 48 chars | `ppFraud_underwriter` is 19. |
| Deployment target name | `^[a-zA-Z][a-zA-Z0-9-]*$`, max 64 | Exactly the inverse: hyphens allowed, **underscores are not**. `pp-prod` passes, `pp_prod` fails. |

<Callout type="warn" title="validate is strict at the root and lax one level down">
The root spec is Zod `.strict()`, so one unknown top-level key fails outright and names
itself:

```console
$ agentcore validate --json
{"success":false,"error":"…/agentcore/agentcore.json:\n  - root: unknown keys (remove): \"canaryKey\""}
```

But *nested* objects are not all strict — an unknown key inside a `runtimes[]` entry is
silently accepted. Do not rely on validate to catch a typo inside a runtime block.

Two documentation sources are also wrong and were checked: the vended
`agentcore/.llm-context/agentcore.ts` declares only 15 of the root's 20 keys, and the
generated `AGENTS.md` advertises `onlineInsightsConfigs` and `runtimeEndpoints` as root
arrays, which the strict root **rejects** — declare either and validate fails. The
compiled Zod schema at
`$(npm root -g)/@aws/agentcore/dist/schema/schemas/agentcore-project.js` is the only
authority.
</Callout>

## `aws-targets.json`: where region and account come from

`agentcore create` writes this file as `[]`, and this repo ships it that way. It is the
**only** place region and account are configured.

```json
[
  {
    "name": "default",
    "description": "Point Predictive fraud underwriting - primary",
    "account": "123456789012",
    "region": "us-east-1"
  }
]
```

- `account` must be exactly **12 digits**; validate rejects anything else.
- `region` is a closed enum of 20 AgentCore regions. Memory is region-restricted *beyond*
  that enum, so a valid target does not guarantee `francisMemory` can be created there.
- **`agentcore deploy` has no `--region`, no `--profile`, no `--agent`.** Credentials come
  from the ambient chain; region and account come from this file only.

<Callout type="error" title="Export AWS_REGION, never rely on AWS_DEFAULT_REGION">
**Symptom.** A deploy or an SDK call fails with what looks like a permissions error, in a
region you did not choose.

**Cause.** The Python SDK's region fallback is
`os.getenv("AWS_REGION") or boto3.Session().region_name or "us-west-2"`
(`bedrock_agentcore/identity/auth.py:339`). It **ignores `AWS_DEFAULT_REGION`** and lands
in us-west-2. `MemoryClient` and `GatewayClient` do the same. A cross-region surprise here
presents as an authorization failure, not a configuration failure.

```bash
export AWS_REGION=us-east-1
export AWS_PROFILE=your-bedrock-profile
```
</Callout>

## `deployed-state.json` must be committed

`agentcore/.cli/deployed-state.json` is a build artifact that is **not** disposable.
`agentcore/.gitignore` ignores `.cli/*` and then negates this one path. Do not "tidy up"
that negation.

**Why.** Credential providers are created *before* CloudFormation runs, out of band, in an
identity pre-step. Their ARNs are recorded **only** in that file, and the CDK app reads
them back on the next synth. Losing the file orphans the providers and breaks the next
deploy.

## Renaming a resource destroys it

<Callout type="error" title="A resource's `name` is its CloudFormation logical id">
Renaming a runtime or a memory in `agentcore.json` **destroys and recreates** it — new
ARN, new endpoint, and for a memory, contents gone. Changing any *other* field updates in
place.

This is not a warning about tidiness; it is the difference between a config edit and a data
loss event. The `deployingPrincipal` IAM policy in `deploy/iam_policy.json` carries
`bedrock-agentcore:Delete*` actions specifically because a rename produces Delete+Create
rather than Update.
</Callout>

## Other verified behaviours worth knowing

<Accordions>

<Accordion title="Deploy exit code 2 means success, not failure">
| Code | Meaning |
|---|---|
| 0 | Deployed. |
| **2** | Deployed **with post-deploy warnings** — this is a pass. `deploy/ci.sh` treats 2 as success. |
| 1 | Failed. A log path is printed under `agentcore/.cli/logs/deploy/`. |

A CI script that tests `-ne 0` will fail a successful deploy.
</Accordion>

<Accordion title="`agentcore import` is not a local operation">
It publishes CDK assets to S3 **before** it can fail. Do not run it "to see what it would
do." This repo's runbook lists it under *what this runbook deliberately does not use*.
</Accordion>

<Accordion title="Container builds are ARM64-only">
Both runtimes use `"build": "CodeZip"` specifically to sidestep needing an ARM64 Docker
builder; the packaged closure is already `aarch64` (you can see
`cpython-312-aarch64-linux-gnu.so` inside the zip). Switching to `Container` requires an
ARM64 build path, and CodeBuild in a VPC then needs an explicit `vpcId`.
</Accordion>

<Accordion title="runtimeVersion defaults to PYTHON_3_14, not to your interpreter">
`agentcore.json` pins `PYTHON_3_12` to match the local interpreter and the tested venv. The
CLI's own default is `PYTHON_3_14`. If you regenerate the config, re-pin it or the deployed
interpreter silently diverges from the one the 1,220 tests ran on.
</Accordion>

<Accordion title="`agentcore package` leaves a staging tree that breaks bare pytest">
`agentcore/<runtime>/staging/` is the runtime's full dependency closure. Several
third-party wheels in there ship test modules with colliding basenames (two copies of
`annotated_types/test_cases.py`, for example), so a bare `pytest` aborts during collection
with `import file mismatch` before reaching a single project test. `deploy/ci.sh` passes
`--ignore=agentcore` for that reason. Both the zips and the staging trees are gitignored.
</Accordion>

<Accordion title="`agentcore dev --runtime` is required in scripts">
With more than one runtime, `agentcore dev --logs` alone stops with
`Error: Multiple runtimes found. Use --runtime to specify which one.` Bare `agentcore dev`
opens an interactive picker instead, so the omission only bites in automation. The default
port is 8080 offset by the runtime's index, so `francis` (index 1) lands on 8081 unless
you pass `-p`.
</Accordion>

<Accordion title="There is no `agentcore destroy`">
The teardown path is: empty the config, then deploy the emptiness.

```bash
agentcore remove all --dry-run
agentcore remove all --yes
agentcore deploy --target default --yes   # --yes is REQUIRED here
```

Deploy detects "no resources defined" as a teardown and refuses to proceed without `--yes`.
</Accordion>

</Accordions>

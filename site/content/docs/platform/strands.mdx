*For the customer's engineer. Every constraint here was hit in this repository and is now asserted by a test.*

Eight specialists run through `asyncio.gather` over eight freshly constructed `Agent` objects,
and both halves of that sentence are forced rather than chosen. Verified on `strands-agents`
**1.26.0** and re-verified on **1.50.2** (see [SDK upgrade](/docs/platform/sdk-upgrade)). Sources:
`agents/fanout.py`, `agents/models.py`, `agents/synthesize.py`.

## Fan-out primitive: gather versus GraphBuilder

`strands.multiagent.GraphBuilder` is the obvious-looking choice for a multi-agent fan-out and it
was rejected on five verified grounds. Any one of them alone would decide it.

| Constraint | `asyncio.gather` (chosen) | `GraphBuilder` | Verdict |
|---|---|---|---|
| Partial failure | `return_exceptions=True` plus a per-agent `try/except` gives 7-of-8 graceful degradation | **Fail-fast on any node error** — one transient 5xx loses the whole adjudication | **gather.** One benchmark run lost two specialists and still validated 21 keys |
| Shared `Agent` instances | Not needed; one fresh Agent per specialist per request | **Forbidden** — correct in itself, but it prevents assembling the graph the way it appears to allow | gather |
| `session_manager` on nodes | Unrestricted | **Forbidden** — rules out the interactive path's memory-backed agents outright | gather |
| Typed results between stages | Objects carrying `usage`, `latency_ms`, `wall_ms`, `cost_usd`, `source` pass through intact | **Stringified between nodes** — destroys exactly the telemetry this engagement exists to produce | gather |
| Measured duration | This process's own `perf_counter()` per leg | `GraphResult.execution_time` comes back **zeroed** | **gather.** A benchmark cannot be built on a zero |

```python
results = await asyncio.gather(*(run(domain) for domain in DOMAINS), return_exceptions=True)
```

A thread pool was also tried and is redundant: `BedrockModel.stream` **already** offloads its
blocking boto3 call through `asyncio.to_thread`, so wrapping a coroutine runner in
`ThreadPoolExecutor` adds a layer of threads that buys nothing.

## An `Agent` instance cannot be invoked concurrently

**Build a fresh `Agent` per specialist per invocation. Nothing at module level.**

`Agent.stream_async` takes a `threading.Lock`. An `Agent` is a stateful conversational object,
not a stateless client, so reusing one across concurrent invocations raises
`ConcurrencyException` from code that looks perfectly ordinary. Worse, if overlap never happens
in testing: `result.metrics.accumulated_usage` is **cumulative** on a reused Agent, so a
module-level Agent silently inflates every measurement after the first.

Constructing eight fresh Agents per application is therefore not a workaround — it is what makes
each one's `accumulated_usage` exactly that request's usage.

## Two concurrency ceilings, invisible until you hit them

Symptom for both: adding concurrency stops helping, wall clock per application rises with load
in a way no single model's latency explains, and nothing errors or warns.

| Ceiling | Default | Effect at eight-way fan-out | Fix in this repo |
|---|---|---|---|
| `BedrockModel` HTTP pool | `max_pool_connections=10`, botocore's default | Eight specialists × N applications all queue on the pool | `agents.models.shared_bedrock_client` raises it to **32** and shares one client across every model |
| `asyncio.to_thread` default executor | `min(32, cpu_count + 4)` — 15 threads on an 11-core box | Caps throughput at roughly two applications in flight **regardless of the pool size you just fixed** | `widen_default_executor`, `EXECUTOR_MAX_WORKERS=64`, once per loop |

Admission is then gated by an `asyncio.Semaphore` sized deliberately **above** the pool, so the
pool stays the binding constraint and the queue forms in Python where it is observable rather
than inside botocore where it is not.

## `read_timeout` is silently dropped when you pass a config

<Callout type="error" title="Supplying boto_client_config resets read_timeout from 120 to 60">
Strands sets `read_timeout=120` on the client it builds for you. Supplying your own
`boto_client_config` **silently replaces** that, dropping the timeout back to botocore's default
of 60. Nothing warns you, and the symptom is reads failing at 60 s on calls that used to survive
to 120.

This bites concretely here: the benchmark's slowest single specialist call was **69.78 s**
(`bustout`, `evals/results/pipeline_14x3_us-east-1.json`). At a 60 s read timeout that call does
not return at all.
</Callout>

```python
Config(
    max_pool_connections=32,     # MAX_POOL_CONNECTIONS
    read_timeout=120,            # READ_TIMEOUT_S — must be restated, not inherited
    connect_timeout=10,          # CONNECT_TIMEOUT_S
    retries={"mode": "adaptive"},
)
```

## Unknown config keys are accepted with only a `UserWarning` [#unknown-config-keys-are-accepted-with-only-a-userwarning]

`BedrockConfig` accepts unknown `**model_config` keys with **only a `UserWarning`**. A kwarg
renamed between releases, or simply mistyped, does not raise — it stops taking effect. Run CI
with `-W error::UserWarning` or a typo becomes permanent silence.

That behaviour is also why `requirements.txt` pins the three libraries whose API surface this
repo reads directly to **exact** versions rather than floors, with the reasoning written in the
file beside each pin.

## Retry tuning: the SDK default costs 4 s on the first throttle

```python
from strands.agent import ModelRetryStrategy      # note the import path

ModelRetryStrategy(max_attempts=4, initial_delay=1, max_delay=8)
```

Read against `strands.event_loop._retry`, that is a ladder of **[1, 2, 4] s** — 7 s worst case.
The SDK's default is `[4, 8, 16, 32, 64, 128] s`, so **one throttle costs 4 s against a
sub-60-second SLA** and a second costs 12.

Two properties bound what a retry can explain:

- It fires on **`ModelThrottledException` and nothing else.** A 5xx is not retried, which is why
  the one degraded run failed *fast* — 21.215 s end to end — rather than slowly.
- A retry sleeps **inside** the call, so it appears as wall clock exceeding the model's own
  reported `latencyMs`. That gap is computable per call, which made "is the tail retries?"
  falsifiable rather than assumed. Measured: **0 `ModelThrottledException` in 336 specialist
  calls**, wall-clock-minus-SDK-latency gap **0.73 s p50 / 1.69 s p95 over n=334**
  (`evals/results/tail_analysis.json`). The tail sits inside the model's own reported latency.
  See [Latency tail](/docs/performance/the-tail).

## Structured output is a kwarg, and `Optional` is a trap

```python
Agent(..., structured_output_model=Adjudication)   # correct
agent.structured_output(...)                        # DEPRECATED
```

An `Optional` field drops out of the generated JSON Schema's `required` array. On a contract
whose whole point is **exactly 21 keys in the customer's order**, a field the model is not
required to emit is a contract violation waiting to happen. `agents/contracts.py` declares all 21
as required, in order, with no `Optional`. Across the 42 benchmark runs `repair_attempts` totalled
**0** and every run validated all 21 keys.

## Two settings that are wrong by default for a stateless call

```python
Agent(
    ...,
    callback_handler=None,                        # the default PRINTS EVERY TOKEN to stdout
    conversation_manager=NullConversationManager(),
)
```

`callback_handler` is the surprising one: a production runtime on the default handler streams
every token of every specialist to stdout, and therefore into CloudWatch Logs.

## Where usage and latency actually live

Everything the benchmark reports comes from these paths and nowhere else.

| Field | Path | Note |
|---|---|---|
| Token usage | `result.metrics.accumulated_usage` | **Cumulative on a reused Agent** — a fresh Agent per invocation is what makes it per-request |
| Cache tokens | `…accumulated_usage.get("cacheReadInputTokens")` / `…("cacheWriteInputTokens")` | **Optional keys** in the TypedDict. Use `.get()`; direct indexing raises |
| Non-cached input | `…["inputTokens"]` | Converse counts **only non-cached** tokens here. Responses' `input_tokens` is the *total* including cached — `agents/mantle.py` normalises to the Converse convention so one rate table prices both families |
| Model latency | `result.metrics.accumulated_metrics["latencyMs"]` | The model's own reported latency, narrower than wall clock |
| Wall clock | this process's own `time.perf_counter()` | Reported separately from model latency, never merged |

Offline means `None`, never zero: in `MOCK_MODE` there is no usage, so `usage` is `None` and
`cost_usd` is `None` — never a plausible-looking guess. The `source` field records which
transport produced a row (`bedrock` / `bedrock-mantle` / `mock`) so a report can separate them
rather than pooling a Converse call, a Responses call and a mock under one label.

## Two transports, chosen by the model id alone

`openai.gpt-5.*` ids are **not on Bedrock Converse** — `converse` rejects them with
`ValidationException: The provided model identifier is invalid` — and are reachable only through
the `bedrock-mantle` Responses endpoint. So a specialist's model assignment alone decides its
transport:

```python
transport_for(model_id)   # reads agents.models.SPECIALIST_MODELS; mantle.is_mantle_model() routes
```

No flag, no second switch. `agents.models.SPECIALIST_MODELS` is the only place the decision is
expressed. The mantle result is wrapped in an adapter carrying the same surface the Converse path
returns (`message`, `usage`, `latency_ms`, `stop_reason`) so result assembly is **shared** rather
than duplicated per family.

Three things the mantle path cannot honestly report, and does not:

| Field | Value on a mantle call | Why not something more plausible |
|---|---|---|
| `stop_reason` | `None` | `mantle.complete` does not surface the Responses `status`, so `"end_turn"` would be a guess |
| `will_cache` | `None` | `cachePoint` and minimum cacheable prefixes are Converse concepts; `False` would be a Converse verdict about a request that carried no cache point |
| `cost_usd` | raises on an unpriced id | An unpriced GPT id surfaces as a recorded error rather than as a call reported at $0 |

## Still unknown

**Nothing here was measured under concurrent load.** Both concurrency ceilings above are read
from the libraries' own defaults and from the code that widens them; the benchmark ran **one
application at a time**, so no measurement on this site says where the widened pool or the
widened executor actually binds. The semaphore's sizing rationale is an argument, not a
measurement.

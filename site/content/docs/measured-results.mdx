Every p99 on this page is a refusal rather than a number. Percentiles below a documented sample
count are refused outright — p50 needs 5, p95 needs 20, p99 needs 100 — and all four rows above
carry the same recorded string: `"p99": "refused: 42 sample(s), need >= 100. A p99 over 42
sample(s) is not a p99."` That string is in the artifact, and nothing on this site launders it
into a figure.

<Callout type="error" title="Two input tokens is why cache-write pricing matters">
The synthesizer reports 2 input tokens and 4,300 cache-**write** tokens per call, because the
whole ~31K-character prompt lands in the cache-write class. GPT-5.6 bills cache-write at
**1.25x input**. Omitting that term under-reported a measured Luna call by **62%**. See
[cost levers](/docs/cost/levers#gpt-56-cache-write-tokens-bill-at-125x-input).
</Callout>

## One degraded run

| Field | Value |
|---|---|
| Run | APP-1011, repetition 3 |
| Failed domains | `synthetic`, `rings` |
| Failure kinds | `synthetic: server_5xx`, `rings: server_5xx` |
| Underlying error (both) | `InternalServerException ... (reached max retries: 2)` on `ConverseStream` |
| Synthesis error | none |
| **Adjudication validated** | **true — all 21 keys** |
| End to end | **21.215 s** |

Three things this single run demonstrates, all of them design intent working:

1. **7-of-8 graceful degradation is real.** Two specialists were lost and the adjudication still
   validated its full 21-key contract.
2. **A 5xx fails fast.** 21.2 s is among the quickest runs in the whole sample. A server error
   here costs a *fraud dimension*, not latency.
3. **Degraded runs are reported, never averaged away.** Quoted from the artifact: *"It stays in
   the latency distribution and leaves the cost distribution."* Hence end-to-end n=42 and cost
   n=41.

## Throttling: zero

Across all 336 specialist calls, `ModelThrottledException` occurred **0** times. Retry ladder in
force was `[1, 2, 4]s` over 4 attempts, and that strategy retries on
`ModelThrottledException` and nothing else. Source: `evals/results/tail_analysis.json`.

That matters because it removes the most common explanation for a tail. See
[why the tail is irreducible](/docs/performance/the-tail).

## What this benchmark did not measure

Reproduced from the artifact's own `caveats` array, because the exclusions are as load-bearing as
the figures.

- **AgentCore Runtime overhead.** *"These calls go to Bedrock (and to bedrock-mantle for the
  synthesizer) directly from the host named in run.host, so container cold start, session setup
  and SSE framing are NOT in the end-to-end figures."*
- **Signal generation.** *"build_payload runs OUTSIDE the timed window because the customer's
  architecture precomputes signals; an end-to-end figure here is agent latency, not
  pipeline-including-ETL latency."*
- **Throughput.** *"Applications were run ONE AT A TIME, so nothing here says what happens when N
  adjudications overlap."*
- **Per-application percentiles.** Computed over 3 repetitions each and *"therefore mostly
  suppressed by design."*

One process note from the same array: aggregates in the file were recomputed from `raw_runs` by
`evals.bench.reaggregate_pipeline_report` at `2026-07-28T07:46:30+00:00`. Measurements are
unchanged and no model was called to produce that recomputation.

## Where the earlier single-run figure fits

`README.md` and `CHANGELOG.md` carry an earlier headline: **37.5 s end-to-end at $0.245** on
APP-1004, one live run.

**The 42-run benchmark is authoritative**: 31.45 s p50 / 46.55 s p95, $0.1440 p50. The 37.5 s
figure is one run on one application and the repo says so in place (*"one measured run on one
application, which is enough to show the target is reachable and not enough to call it a
benchmark"*). Neither contradicts the other — APP-1004's three benchmarked repetitions ran 37.8 / 36.2
/ 39.2 s, which brackets 37.5 s neatly — but only one of them is a distribution. Quote the p50
with its n.

`media/demo-poster.png` as its poster frame.

*For the customer's engineer. This page answers, rule by rule, the risk she named herself. Every count is read from `signal_layer/rules/catalog.py:CATALOG` at import and matches the generated table in `docs/general_rules_coverage.md`.*

**29 numbered rules: 27 enforced by deterministic tested code, 2 by the verbatim prompt text.**
Replicating the semantic layer's guardrails was named as the biggest risk in the migration — in her
words, *"replicating the SQL guardrails built into snowflake cortex by the semantic layer"* — so the
rules became code with one module per rule, not prose in a prompt.

Summing the first four gives the 27 enforced in code. `tests/test_rules.py` collects **67 tests**
(`MOCK_MODE=1 python3 -m pytest tests/test_rules.py -q --collect-only`).

Why exactly two rules are prompt-enforced, and why that is correct rather than a gap. **Rule 20** is
score *interpretation* — what an IncomePass score means, and that income overstatement in isolation
is not correlated to early payment default while overstatement combined with other misrepresentation
is. That belongs in the model's context, not in a function; `signal_layer.bands.INCOMEPASS_SEMANTICS`
carries the verbatim semantics and `test_rule_20_incomepass_semantics_in_prompts` asserts the text
reached the loaded prompts. **Rule 22** is a **ban on a statistic**, not a computation to perform: do
not average fraud scores, because they are standard-scaled. Nothing exists to implement, so what is
asserted instead is that nothing in this repository computes `AVG(fraud_score)`, plus that the caveat
text is present in the prompts. A function that "enforced" either one would be theatre.

<Callout type="info" title="Why the rules had to become code">
The prior revision represented the entire rule set as **six prose display strings**. A rule expressed
only as prose in a prompt is enforced by the model's attention budget; a rule expressed as a tested
function is enforced by the process.

Two of these rules make the difference concrete. Rule 17 is a null-safe exclusion filter whose naive
form silently deletes every legitimate application with no email on file. Rule 23 is an absolute
prohibition on raw SSN values.
</Callout>

## Rules where the naive reading is a real defect

Twenty-nine rules do not carry equal weight. These are the ones where implementing the obvious
version produces a wrong answer, with the failure each one causes. Notes taken from
`docs/general_rules_coverage.md`.

| Rule | Naive implementation | What it produces | Implemented by |
|---|---|---|---|
| **17** | `<> ALL (...)` without the `or ... is null` disjunct she explicitly writes | **Silently deletes every legitimate application with no email on file** — in SQL, `NULL <> ALL (...)` is NULL, not true. Highest-risk rule in the set | `exclude_fake_records`, `phone_excluded`, `validate_exclusion_sql` in `signal_layer/rules/r17_fake_records.py` |
| **15** | Count NULL `borr_ssn` as a distinct SSN | Inflates every reuse count by one and manufactures a shared-identifier cluster out of a missing value — a **false positive** against the anti-false-positive discipline the whole prompt set is built around | `count_distinct_ssns`, `is_present_ssn` |
| **26** | Compare phone strings without normalising to the last 10 digits | The opposite failure, a **false negative**: `14724933572` and `4724933572` are the same phone, so reuse counts undercount and a real shared-phone ring is missed. Also required upstream of rule 17's phone exclusion, so getting it wrong corrupts two rules | `norm_phone`, `same_phone` |
| **7** | Blanket `AND chargeoff_flag = false` | **Under-counts defaults.** The rule excludes *pure* chargeoffs — the flag set with **neither** EPD flag. The full chargeoff × (epd, epd6) truth table is tested | `is_default`, `is_pure_chargeoff`, `default_rate` |
| **9** | Two-valued co-borrower resolution | Turns a data gap into a finding. PRESENT / ABSENT / UNKNOWN must stay three-valued because the identity agent escalates on "no co-borrower" but not on "not sourced" | `resolve_coborrower` |
| **10** | Treat NULL activity as active | The customer does not state the NULL branch. `NULL` is not `> 0`, so unknown activity is excluded, and the decision is recorded as `ACTIVE_DEALER_NULL_NOTE` rather than left implicit | — |
| **19** | `%CRESCENT%` wildcard | **Double-counts two institutions.** Rule 1.5 itself supplies `CRESCENT` as a nickname, which matches both Crescent Bank and `FCRACRESCENTBANK`. Rules 1.5, 16 and 19 are resolved together by one lender resolver for that reason | one lender resolver; rule 16 is the mirror case — Stellantis resolves to **two** names, so `LenderResolution.lender_names` is a tuple and `.lender_name` raises on a multi-name result |
| **27** | Trust a prompt instruction to "limit to 5" | A prompt instruction is a request. `QueryBudget` is a ceiling: the budget is spent **before** a call is issued, so the sixth call cannot be made. Shared with rules 13 and 18, since a rule-18 retry costs a rule-27 call | `QueryBudget` |

Rules 0.5 and 6 are the same rule under two ids, and both appear deliberately. Rule 6 is
byte-identical to rule 0.5 in the identity document, and one implementation serves both. Quoting the
coverage doc: *"deduplicating in code is correct, deduplicating in the inventory is not"* — so both
ids are listed, and the count of 29 is the customer's count rather than a tidied one.

## Rule 23 and the one hard compliance boundary

Rule 23 is the only rule she **capitalises**: never include raw SSN values or any parts of them, only
hashed values. It is enforced as a **recursive gate** over the payload —
`assert_no_raw_ssn` / `find_raw_ssn` in `signal_layer/rules/r23_no_raw_ssn.py` — rather than as a
prompt instruction, because a prompt instruction is not a compliance control.

<Callout type="error" title="Known gap: rules 12 and 23 both want a Bedrock Guardrail, and none is configured">
Quoting `docs/general_rules_coverage.md` directly: *"No `guardrailIdentifier` or `apply_guardrail`
call exists anywhere in it."*

Rule 23 is enforced by the recursive payload gate and rule 12 by a post-generation validator. Both
are real and both are tested. Neither is the platform-level block the customer's compliance posture
should ultimately have, **because a validator in the same process can be bypassed by a code path that
forgets to call it.**

Recorded as a gap in `r23_no_raw_ssn.ENFORCEMENT_LAYERS` and in the coverage document, and
`bedrock-guardrail` is deliberately never used as the *sole* layer for any rule. It is a platform
configuration item for the migration, not a code change.
</Callout>

## What "enforced in code" does and does not mean

Three honest boundaries, stated because a review will look for them.

1. **Rules are extracted from one document of eight.** The identity orchestration document carries
   the longest form of all 29. The other seven differ — rule 6 is absent from some, and rules 11, 13,
   17, 18, 20 and 24 are worded differently or truncated per agent.
   `signal_layer.rules._source.variants_of()` reports the differences and
   `test_rule_variants_across_documents` pins them.
2. **Several rules govern SQL this repository does not execute.** Rules 1, 4, 5, 8, 11 and 13 are
   about query construction. What exists for them is a **resolver plus a SQL validator** —
   `validate_lender_join_sql`, `validate_join_sql`, `validate_date_sql`, `validate_retro_sql`,
   `validate_no_deprecated_tables` — so each rule is checkable against whatever generates the query,
   whether that is this signal layer or the customer's existing pipeline. That is a genuine
   difference from "the rule runs in production", and it should be said in the room.
3. **Rule 1.5 does not guess.** The rule's own words are *"don't hallucinate."* An unresolved lender
   input returns `resolved=False` rather than a best-effort match.

## Regenerating the coverage document

```bash
python -m signal_layer.rules.catalog > docs/general_rules_coverage.md
MOCK_MODE=1 python3 -m pytest tests/test_rules.py -q          # 67 tests
```

The second command asserts the generated file matches the catalog, so the document cannot be edited
into agreement with a claim the code does not support.

## Still unknown

- **Whether the per-agent rule variants matter.** Seven documents differ from the identity document
  in six rules, and which wording the customer considers authoritative is her call.
- **Whether a Bedrock Guardrail is wanted.** Rules 12 and 23 both point at one; none is configured.
- **Whether the SQL validators match her production query generator.** They are checkable against it;
  they have not been run against it.

## The risk this answers

The customer's engineer named replicating the semantic layer's guardrails as the biggest risk
in the migration — in her words, *"replicating the SQL guardrails built into snowflake cortex
by the semantic layer."*

Those guardrails are a numbered list of General Rules, repeated across all eight specialist
orchestration documents. There are **29 of them**, and they are not stylistic guidance: rule
17 is a null-safe exclusion filter whose naive form silently deletes every legitimate
application with no email on file, and rule 23 is an absolute prohibition on raw SSN values.

<Callout type="warn" title="Why they had to become code, not prose">
The prior revision of this repository represented the entire rule set as **six prose display
strings**. A rule expressed only as prose in a prompt is enforced by the model's attention
budget. A rule expressed as a tested function is enforced by the process.

`signal_layer/rules/` is one module per numbered rule plus `catalog.py`. `tests/test_rules.py`
collects **67 tests**
(`MOCK_MODE=1 python3 -m pytest tests/test_rules.py -q --collect-only`).
</Callout>

<Callout type="info" title="Why exactly two rules are prompt-enforced, and why that is correct">
- **Rule 20** is score *interpretation* — what an IncomePass score means, and that income
  overstatement in isolation is not correlated to early payment default while overstatement
  combined with other misrepresentation is. That belongs in the model's context, not in a
  function. `signal_layer.bands.INCOMEPASS_SEMANTICS` carries the verbatim semantics and
  `test_rule_20_incomepass_semantics_in_prompts` asserts the text reached the loaded prompts.
- **Rule 22** is a **ban on a statistic**, not a computation to perform: do not average fraud
  scores, because they are standard-scaled. There is nothing to implement. What is asserted
  instead is that nothing in this repository computes `AVG(fraud_score)`, plus that the
  caveat text is present in the prompts.

Neither is a gap. A function that "enforced" either one would be theatre.
</Callout>

## The rules where the naive reading is a real defect

Twenty-nine rules do not carry equal weight. These are the ones where implementing the
obvious version produces a wrong answer, taken from the implementation notes in
`docs/general_rules_coverage.md`.

<Accordions type="single">

<Accordion title="Rule 17 — the highest-risk rule in the set">

The rule asks for records with fake emails, common consortium VINs and common consortium
phones to be filtered out. The naive `<> ALL (...)` predicate, without the `or ... is null`
disjunct the customer explicitly writes, **silently deletes every legitimate application with
no email on file** — in SQL, `NULL <> ALL (...)` is NULL, not true.

The phone carve-out is also implemented as she states it: a record is excluded only if a
borrower phone is in the common list **and no other valid phone number exists**.

Implemented by `exclude_fake_records`, `phone_excluded`, `validate_exclusion_sql` in
`signal_layer/rules/r17_fake_records.py`.

</Accordion>

<Accordion title="Rule 15 — one uncounted NULL fabricates an identity cluster">

NULL `borr_ssn` is not a distinct SSN. Counting it inflates every reuse count by one and
manufactures a shared-identifier cluster out of a missing value — a false positive against
exactly the anti-false-positive discipline the whole prompt set is built around.

Implemented by `count_distinct_ssns`, `is_present_ssn`.

</Accordion>

<Accordion title="Rule 26 — the opposite failure: a false negative">

`14724933572` and `4724933572` are the same phone. Without normalising to the last 10 digits,
reuse counts **undercount** and a real shared-phone ring is missed. This rule is also required
upstream of rule 17's phone exclusion, so getting it wrong corrupts two rules.

Implemented by `norm_phone`, `same_phone`.

</Accordion>

<Accordion title="Rule 7 — the wrong reading under-counts defaults">

Exclude *pure* chargeoffs — applications carrying the chargeoff flag but **neither** EPD flag.
The tempting simplification, a blanket `AND chargeoff_flag = false`, under-counts defaults.
The full chargeoff × (epd, epd6) truth table is tested.

Implemented by `is_default`, `is_pure_chargeoff`, `default_rate`.

</Accordion>

<Accordion title="Rule 9 — three-valued, because 'absent' and 'unknown' are different">

Co-borrower resolution returns PRESENT / ABSENT / UNKNOWN. "No co-borrower" and "not sourced"
must not collapse into one value, because the identity agent escalates on the former. A
two-valued implementation turns a data gap into a finding.

Implemented by `resolve_coborrower`.

</Accordion>

<Accordion title="Rule 10 — the NULL branch the customer does not state">

A dealer is active when `consortium_number_of_apps_last_1_year > 0`. NULL is not `> 0`, so
unknown activity is excluded. The customer does not state this; the branch is explicit,
tested, and recorded as `ACTIVE_DEALER_NULL_NOTE` so the decision is visible rather than
implicit.

</Accordion>

<Accordion title="Rule 19 — a nickname from rule 1.5 collides with it">

Only `CRESCENTBANK` may match Crescent Bank, never `FCRACRESCENTBANK`. But rule 1.5 itself
supplies `CRESCENT` as a nickname, and a naive `%CRESCENT%` wildcard matches **both**
institutions and double-counts. Rules 1.5, 16 and 19 are resolved together by one lender
resolver for that reason.

Rule 16 is the mirror case: Stellantis resolves to **two** lender names, which is why
`LenderResolution.lender_names` is a tuple and `.lender_name` raises on a multi-name result.

</Accordion>

<Accordion title="Rule 27 — mechanical, not prompt-trusted">

Max 5 SQL calls per request. The budget is spent **before** a call is issued, so the sixth
call cannot be made. A prompt instruction to "limit to 5" is a request; `QueryBudget` is a
ceiling. Shared with rules 13 and 18, since a rule-18 retry costs a rule-27 call.

</Accordion>

<Accordion title="Rules 0.5 and 6 — the same rule, two ids, deliberately both listed">

Rule 6 is byte-identical to rule 0.5 in the identity document. One implementation serves both.
Quoting the coverage doc: *"deduplicating in code is correct, deduplicating in the inventory is
not"* — so both ids appear in the table, and the count of 29 is the customer's count, not a
tidied one.

</Accordion>

</Accordions>

## Rule 23, and the one hard compliance boundary

Rule 23 is the only rule the customer **capitalises**: never include raw SSN values or any
parts of them, only hashed values. It is enforced as a **recursive gate** over the payload —
`assert_no_raw_ssn` / `find_raw_ssn` in `signal_layer/rules/r23_no_raw_ssn.py` — rather than as
a prompt instruction, because a prompt instruction is not a compliance control.

<Callout type="error" title="Known gap: rules 12 and 23 both want a Bedrock Guardrail, and this repo does not configure one">
Quoting `docs/general_rules_coverage.md` directly: *"No `guardrailIdentifier` or
`apply_guardrail` call exists anywhere in it."*

Rule 23 is enforced by the recursive payload gate and rule 12 by a post-generation validator.
Both are real and both are tested. Neither is the platform-level block the customer's
compliance posture should ultimately have, **because a validator in the same process can be
bypassed by a code path that forgets to call it.**

This is recorded as a gap in `r23_no_raw_ssn.ENFORCEMENT_LAYERS` and in the coverage document,
and `bedrock-guardrail` is deliberately never used as the *sole* layer for any rule. It is a
platform configuration item for the migration, not a code change.
</Callout>

## What "enforced in code" does and does not mean

<Callout type="warn" title="Three honest boundaries">
1. **The rules are extracted from one document of eight.** The identity orchestration document
   carries the longest form of all 29. The other seven differ — rule 6 is absent from some, and
   rules 11, 13, 17, 18, 20 and 24 are worded differently or truncated per agent.
   `signal_layer.rules._source.variants_of()` reports the differences and
   `test_rule_variants_across_documents` pins them.
2. **Several rules are about SQL this repository does not execute.** Rules 1, 4, 5, 8, 11 and
   13 govern query construction. What is implemented for them is a **resolver plus a SQL
   validator** — `validate_lender_join_sql`, `validate_join_sql`, `validate_date_sql`,
   `validate_retro_sql`, `validate_no_deprecated_tables` — so the rule is checkable against
   whatever generates the query, whether that is this signal layer or the customer's existing
   pipeline. That is a genuine difference from "the rule runs in production", and it should be
   said in the room.
3. **Rule 1.5 does not guess.** The rule's own words are *"don't hallucinate."* An unresolved
   lender input returns `resolved=False` rather than a best-effort match.
</Callout>

## Parallel speed-up

Fan-out against the sequential counterfactual, one ratio per run, n=42:

| min | p50 | p95 | max | mean |
|---:|---:|---:|---:|---:|
| 1.85x | **3.64x** | 4.99x | 5.11x | 3.73x |

Reporting a distribution rather than a single number is the artifact's own insistence: *"One
speed-up per run, not one number for the port. The spread is the finding: the fan-out is bounded
by its slowest dimension, so the ratio moves with which specialist ran long."*

Both extremes make that concrete. **1.85x** is APP-1001 rep 2, where `income` stalled at 66.01 s
and dominated a 123.28 s sum-of-eight. **5.11x** is APP-1004 rep 3, where the eight specialists
were more evenly loaded across a 173.00 s sum-of-eight, the largest total work in the sample.

What the counterfactual is, quoted: *"sum_of_eight_ms is the SEQUENTIAL COUNTERFACTUAL, the sum of
the eight specialists' own measured wall clocks in this run. It is what eight calls cost one after
another only if each would take the same time alone; the terms are measured, the arrangement is
hypothetical."* The one thing it cannot account for is that a sequential run would issue its eight
calls at eight different moments, and this sample shows Bedrock's per-call generation speed
varying enough to matter.

| Token class | Total | Mean per call |
|---|---:|---:|

| **Cache write** | **180,610** | **4,300.2** |

Total $0.44686675, mean **$0.010640** per call — about **7%** of a median adjudication.

Two input tokens per call is not a measurement error, and it is why cache-write pricing matters
here. The whole ~31K-character synthesis prompt lands in the **cache-write** class on this
transport, and GPT-5.6 bills cache-write at **1.25x input**; omitting that term under-reported a
measured Luna call by **62%**. [Cost
levers](/docs/cost/levers#gpt-56-cache-write-tokens-bill-at-125x-input).

`repair_attempts` totalled **0** across all 42 runs and `runs_needing_a_repair` was 0, so the
21-key structured output validated first time every time — including on the degraded run where
two of the eight narratives were missing.

## One degraded run

| Field | Value |
|---|---|
| Run | APP-1011, repetition 3 |
| Failed domains | `synthetic`, `rings` |
| Failure kinds | `synthetic: server_5xx`, `rings: server_5xx` |
| Underlying error (both) | `InternalServerException ... (reached max retries: 2)` on `ConverseStream` |
| Time each failed call spent before failing | synthetic 8.57 s, rings 8.02 s |
| Synthesis error | none |
| **Adjudication validated** | **true — all 21 keys** |
| End to end | **21.215 s** |

Three things this single run demonstrates, all of them design intent working:

1. **7-of-8 graceful degradation is real.** Two specialists were lost and the adjudication still
   validated its full 21-key contract with zero repair attempts. That is the specific behaviour
   `strands.multiagent.GraphBuilder` cannot provide, being fail-fast on any node error — [why
   GraphBuilder was rejected](/docs/platform/strands).
2. **A 5xx fails fast.** 21.2 s is among the quickest runs in the sample, so a server error here
   costs a **fraud dimension**, not latency — the opposite shape from [the
   stall](/docs/performance/the-tail), which costs latency and loses nothing.
3. **Degraded runs are reported, never averaged away.** Quoted: *"It stays in the latency
   distribution and leaves the cost distribution."* Which is why end-to-end is n=42 and cost is
   n=41.

## Throttling: zero

Across all 336 specialist calls, `ModelThrottledException` occurred **0** times. The retry ladder
in force was `[1, 2, 4]s` over 4 attempts, and that strategy retries on `ModelThrottledException`
and nothing else. Source: `evals/results/tail_analysis.json`.

`stop_reasons` over the 336 calls: `end_turn` **334**, `None` **2** — the two 5xx failures. No
call in the sample was truncated.

## What this benchmark did not measure

Reproduced from the artifact's own `caveats` array, because the exclusions are as load-bearing as
the figures:

- **AgentCore Runtime overhead.** *"These calls go to Bedrock (and to bedrock-mantle for the
  synthesizer) directly from the host named in run.host, so container cold start, session setup
  and SSE framing are NOT in the end-to-end figures."*
- **Signal generation.** *"build_payload runs OUTSIDE the timed window because the customer's
  architecture precomputes signals; an end-to-end figure here is agent latency, not
  pipeline-including-ETL latency."*
- **Throughput.** *"Applications were run ONE AT A TIME, so nothing here says what happens when N
  adjudications overlap."*
- **Per-application percentiles.** Computed over 3 repetitions each and *"therefore mostly
  suppressed by design."*
- **Any p99.**

One process note from the same array: aggregates were recomputed from `raw_runs` by
`evals.bench.reaggregate_pipeline_report` at `2026-07-28T07:46:30+00:00`. *"The measurements are
unchanged... No model was called to produce this file."*

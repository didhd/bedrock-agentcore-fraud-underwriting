## Shape of one fixture

```json
{
  "application_id": "APP-1004",
  "scenario": "…", "why_this_fixture_exists": "…",
  "synthetic_data_notice": "…", "semantic_layer_rev": "…", "computed_at": "…",
  "application": { … 26 core fields, hash_ssn only … },
  "signals":  { … every registry signal … },
  "context":  { … the paired *_context row for each … },
  "alerts_fired": [ … {alert_id, categories, finding_text} … ],
  "expected": { … the pinned adjudication + per-domain band, flag, requirement_id, customer_rule … },
  "notes": [ … why the hard calls are what they are … ]
}
```

Two properties worth stating for a reviewer:

- **Every signal in the registry has a value and a paired `_context` value.** The context row
  is not decoration: the specialists are required to validate signals against it, and the
  fixtures are built so the benign explanation lives *only* there. An agent that ignores
  `_context` gets these wrong.
- **`expected` is not just a band.** Each domain entry is
  `{band, flag, requirement_id, customer_rule}`. The `requirement_id` (e.g. `EMP-017`,
  `MSTR-039`, `STRW-008`) is the addressable unit of disagreement.

<Callout type="warn" title="These are synthetic records">
No customer data is in this repository. Every application, name, SSN hash, dealer and employer
is fabricated to exercise a specific rule, which each file states in its own
`synthetic_data_notice`. That is also why a pin disagreement is
[a fixture question at least as much as a model question](/docs/measured-results#verdict-stability).
</Callout>

that skewed toward fraud would reward a model that escalates everything.

## The nine anti-false-positive scenarios

<Callout type="warn" title="Count precisely: five designated fixtures, nine scenarios">
`evals/set_comparison.py::ANTI_FP_APPS` designates **five** applications
(APP-1006 … APP-1010) — the records built entirely to be false-positive traps, all of which
must resolve LOW across every domain.

**Four more anti-false-positive controls are embedded inside records that are not themselves
LOW overall**, so a single domain has to clear independently while the adjudication does not.
Those are the harder tests, and they are not in `ANTI_FP_APPS` because the *application* is not
benign — only that domain is.

Nine scenarios, five fixtures. Both numbers are correct about different things.
</Callout>

### The five designated fixtures

<Accordions>

<Accordion title="APP-1006 — every employer contact field null → EMP-007 data gap">
Employer address, phone, city, state and ZIP are **all null** and the employer name is vague
("Sunset Services") — exactly the pair of conditions the employment prompt calls data quality
rather than fraud. `EMP-018` states the outcome directly: *"Missing fields alone = LOW."*

Two details that make it a real test rather than a soft one:

- Both fired alerts share the same `underlying_behavior` ("incomplete employer record"). **Two
  alerts from one data gap is one signal.**
- `employer_phone_distinct_ssn_count` is `0` **because the phone itself is null** — and its
  `_context` row says so explicitly, so an agent cannot read the zero as "no sharing
  observed". A model that reads `_context` gets this; one that reads only signals invents a
  clean phone.

This is the fixture `evals/datasets/underwriting_golden.jsonl` references by name
(`fp_employer_all_null_contact_fields_low`).
</Accordion>

<Accordion title="APP-1007 — dealer consortium 940, 15% EPD, zero coordination → DLR-009 / DLR-010">
The dealer prompt's CRITICAL DISTINCTION, isolated from every confound. The dealer's portfolio
metrics are **as bad as they get** — 940 consortium score, 940 risk score, 15% EPD, 18%
default rate — and there is *zero* coordination evidence: no phone reuse at the dealer, no
employer concentration, no identity patterns.

`DLR-009` forbids escalating on score alone. But note `DLR-010` is a **positive obligation**,
not only a prohibition: her wording requires the analysis to report the portfolio risk metrics
factually while classifying them as credit-risk context rather than fraud evidence. **A dealer
analysis that omits the 940 score is as wrong as one that escalates on it.**

All three fired alerts share `underlying_behavior` "dealer portfolio performance" — one fact
reported three ways. And the pairing is the point: APP-1004 *also* carries a 900+ dealer score,
but there it sits beside real coordination evidence. This record is that score with the
coordination removed.
</Accordion>

<Accordion title="APP-1008 — military-base employer, 3,100 SSNs → EMP-017 + DLR-015 together">
`EMP-017` names *"Large national employers, military, government, staffing agencies, and gig
platforms"* as explicitly NOT a fraud signal, and `DLR-015` says employer concentration is
*"Normal for dealers near large employers/bases"*. This record maximises **both** numbers at
once so the two rules are exercised together rather than singly.

`employer_spike_flag` fires and must still clear — `EMP-015` says a spike *"may reflect hiring
surge, not fraud"* and the context gives the specific cause (annual PCS season, with the prior
three quarters' counts to prove the seasonality). The 34% employer concentration is above
`DLR-015`'s 20% threshold, but that threshold is qualified *"at small dealers with few apps"*
and this dealer has 2,100 applications in 24 months and sits 1.2 miles from the gate.
</Accordion>

<Accordion title="APP-1009 — 96 SSNs at the building, 1 at the unit → RNG-013 benign overlap">
`RNG-013`'s benign-overlap rule at **maximum magnitude**. Building-level address reuse is 96;
exact-unit reuse is 1.

`address_reuse_distinct_ssn_count = 96` is the largest reuse number in the whole fixture set
and must produce the **lowest possible concern** — while APP-1004 escalates on **6**, because
5 of its 6 are in *one unit*. That pair is the contrast `SYN-010` and `RNG-014` describe, and
it is why the record exists: **a big number alone cannot move the band.**

Three of its four alerts share `underlying_behavior` "dense multi-unit building address", and
`fraud_score 356` sits in the customer's medium band and must not by itself move the outcome.
</Accordion>

<Accordion title="APP-1010 — eleven alerts, one behaviour → IDEN-014 / IDEN-018 / RNG-023">
The **most repeated guardrail in the corpus**, isolated: alert volume on its own does not
indicate risk, and several alerts sharing one underlying behaviour count as one signal —
stated in her own words at `IDEN-018`, `INC-019`, `SYN-020` and, in the bustout/rings
phrasing, `BST-024` and `RNG-023`.

Eleven alerts fire across **five** General Rule 3 categories, and all eleven carry the same
`underlying_behavior`. Ten separate signals are elevated —
`phone_reuse_distinct_ssn_count`, `phone_ssn_count`, `phone_reuse_count_this_dealer`,
`address_reuse_distinct_ssn_count`, `address_ssn_count_same_unit`,
`address_ssn_count_same_building`, `email_reuse_distinct_ssn_count`,
`coborrower_appears_as_borrower_count`, `borrower_appears_as_coborrower_count`,
`coborr_distinct_primary_borrowers_count` — **all by the single fact that four relatives share
one house and one phone number. Ten signals, one concern.**

Two of those signals are above their stated bands: `phone_ssn_count = 4` exceeds `SYN-011`'s
"1-2 normal", and `phone_reuse_count_this_dealer = 3` exceeds `DLR-014`'s "0-1 is normal". Both
bands are **qualified** — `SYN-011` by *"with unrelated identities"*, `DLR-014` by *"with high
fraud scores"* — and neither qualifier holds: all four identities share a surname and an
address.

`fraud_score 598` sits in the medium band. **A counting-based decision rule escalates this
record on eleven alerts and a medium score. The customer's rules require LOW.** This is the
single best fixture for telling a genuine implementation from a plausible one.
</Accordion>

</Accordions>

### The four embedded controls

| Fixture | Overall pin | The domain that must clear independently, and why |
|---|---|---|
| **APP-1001** | LOW | The full control: *every* suspicious value has a benign cause stated only in its own `_context` row — a 40-unit complex, a first-time buyer's `ssn_days_in_system = 0`, a 480-SSN employer that is a hospital. `IDEN-013` calls a zero-day SSN *"common for first-time buyers. Only concerning with other velocity signals"* — and there are none. |
| **APP-1002** | LOW | The **alert-volume control**: 5 alerts fire, 4 of them from one shared household phone (`IDEN-014`), so volume must not move the band (`IDEN-018`). Also `fraud_score 388`, in the medium band, which must still resolve LOW — a score is a model output, not corroborated evidence. |
| **APP-1005** | MEDIUM | The **staffing-agency control inside a non-benign record.** The employer carries 260 SSNs, 40 new in 90 days, `rapid_employer_change_flag` **and** `employer_spike_flag` — all four with a staffing-agency explanation in their own `_context` rows, and `EMP-017` names staffing agencies. `employment` must be LOW while the adjudication is MEDIUM. Also `fraud_score 712` — the customer's *high* band — on a record that must stay MEDIUM (`MSTR-029`). |
| **APP-1011** | LOW | The **anti-padding control.** `alerts_fired` is deliberately **empty** — the only record that proves the payload builder and the specialists handle a zero-length array. `STRW-005` caps straw at 2–3 sentences with no co-borrower, and unlike APP-1003 there is nothing else on the record to pad from. Its `_context` rows also distinguish *"no co-borrower exists"* from *"a co-borrower exists with a count of zero"* — both render as `0` in the signal, and only the context says which. |

## The pinned expectations, and the hard calls

The `notes` array on each fixture explains the calls a reviewer would question. Four patterns
recur and each is a rule the customer stated:

<Tabs items={['Band ≠ flag', 'Overlap is not corroboration', 'Sparse data alone vs sparse data plus', 'A score is not evidence']}>
<Tab value="Band ≠ flag">

A domain can be **POSSIBLE with its flag at 0**. `MSTR-039` sets a flag to 1 only on *"clear,
material, corroborated evidence"*.

- **APP-1004**: `dealer_flag = 0` while the dealer band is POSSIBLE. `DLR-009` forbids
  escalating on the 930 consortium score, and `DLR-018` says negative-file and
  synthetic-linkage flags are *individual borrower* flags meaning dealer fraud *"only if
  multiple such borrowers cluster at one dealer"*.
- **APP-1014**: **all eight flags are 0 while the overall outcome is MEDIUM.** That combination
  is legal and important — `MSTR-027`'s MEDIUM (*"unresolved fraud concerns supported by
  moderate corroborating evidence… requiring additional verification"*) is exactly this record.
  **A flag-counting implementation returns LOW.**
- **APP-1005**: `income` is POSSIBLE with `income_flag = 0` — 18% overstatement is in the
  "requires context" band and the context (assignment-based hours) supplies it.

</Tab>
<Tab value="Overlap is not corroboration">

`MSTR-022` warns that overlapping references are not automatic independent corroboration.

- **APP-1012**: `straw_flag` is the **only** flag set to 1. Identity, dealer, bustout and rings
  are all POSSIBLE because they see genuine spillover — but the phone sharing, the dealer
  clustering and the loan-to-income ratio are **the same straw arrangement viewed from four
  angles**, so only straw earns a flag.
- **APP-1013**: `employment_flag = 1` while `income_flag = 0`, both bands POSSIBLE. The
  employer's fabrication indicators are independent of each other; the 39% overstatement is a
  *consequence* of the same unreachable employer.
- **APP-1014** is the contrast: three concerns resting on **three separate underlying facts**,
  so unlike APP-1010 they are not one signal counted three times. Its email overlap is the one
  indicator in the whole set whose `_context` row explicitly states that no benign explanation
  is available.

</Tab>
<Tab value="Sparse data alone vs sparse data plus">

`EMP-019` defines employment POSSIBLE as three conjuncts: *"no verifiable presence +
coordinated SSN clustering + abnormal velocity."*

**APP-1006 has the first alone and must be LOW. APP-1013 has all three and must be POSSIBLE.**
APP-1006's employer record is in fact *emptier* than APP-1013's. Without both records the rule
is only half-tested — and a model tuned on either one alone will get the other wrong.

APP-1006 also carries the strongest available argument that blankness is a source-data
property: the same borrower cited the same blank-record employer on **4 applications across 3
years**.

</Tab>
<Tab value="A score is not evidence">

Four fixtures place `fraud_score` in a band that argues against the pinned outcome, so a model
that leans on the score fails them:

| Fixture | `fraud_score` | Customer band | Pinned outcome |
|---|---:|---|---|
| APP-1009 | 356 | medium | LOW |
| APP-1002 | 388 | medium | LOW |
| APP-1010 | 598 | medium | **LOW**, against 11 alerts |
| APP-1005 | 712 | **high** | MEDIUM |

`FRAUD_SCORE_NO_PREFILTER_RULE` (General Rule 22's neighbour) also forbids limiting
investigation to scores above 700, so the score cannot be used as a gate either.

</Tab>
</Tabs>

## The golden dataset built on top

`evals/datasets/underwriting_golden.jsonl` — **13 scenarios, 134 assertions** — in the
`AGENTCORE_EVALUATION_PREDEFINED_V1` shape, and it parses under the AgentCore CLI's own
`parseAndValidate`.

| Group | Scenarios | Expected trajectory |
|---|---:|---|
| End-to-end adjudications (APP-1001…1005) | 5 | all eight specialist calls |
| Anti-false-positive, one domain each | 5 | the single relevant specialist |
| Format contracts (straw 2–3 sentences) | 1 | `call_straw_agent` |
| Interactive Francis (2-tool cap + format; RETRO deflection) | 2 | 1 tool / none |

Two extra keys are carried for review and ignored by the CLI's parser:

- **`expected_provenance`** — which fixture `expected` block the scenario encodes, **plus the
  exact verbatim prompt line each assertion comes from**, quoted as
  `prompts/verbatim/<file>::<SECTION> -> '<line>'`. Every one of the 134 assertions is
  traceable to a line in the customer's own prompt.
- **`notes`** — why a scenario exists where that is not self-evident.

## Regenerating

```bash
python3 -m fixtures.regenerate      # rewrites fixtures/applications/*.json
```

The scenario modules are deliberately importable without side effects (`_build` writes,
`_scenarios_*` only declare, `__init__` never writes), so a test can read a scenario without
touching the tree. `regenerate` also fails on duplicate application ids before writing
anything.

`tests/test_fixtures.py` asserts that the fixture-side signal mirror agrees with
`signal_layer/registry.py` **name for name** — the registry is the authority and the fixtures
are checked against it, not the other way round.

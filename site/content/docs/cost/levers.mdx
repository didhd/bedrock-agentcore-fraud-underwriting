*For both audiences, but the exclusions are the part that matters. Every figure here comes from `agents/pricing.py` on the published rate card or from a measured usage record.*

**Three levers survive arithmetic, and [three more look like levers and are not](/docs/cost/what-does-not-work).** The `global.*` inference profile is worth exactly **−9.09%** on the Claude calls, batch inference **−50%** where Bedrock offers it — which on this assignment is 3.58% of the bill — and removing per-application Cortex Analyst calls eliminates eight Analyst messages and eight warehouse executions per application.

## Which lever applies to us

| Lever | Measured effect | Applies here? | Worth on this assignment |
|---|---|---|---:|
| `global.*` instead of `us.*` inference profile | **exactly −9.09%** per rate category, identical API | **Yes**, on the 8 Claude calls | **−9.09%** on specialists, **−8.38%** blended |
| Batch inference | **−50%** where offered | **Partly** — `dealer` and `straw` only | **−3.58%** |
| Precomputed signals instead of per-application Cortex Analyst | 8 Analyst messages + 8 warehouse executions removed per application | **Yes**, structurally | **Not priced** — we lack their credit rate |
| Per-agent model tiering | **$0.00** structurally, by arithmetic | No | **0%**. [Detail](/docs/cost/what-does-not-work#per-agent-tiering-saves-000-structurally) |
| Prompt caching | Engages on **0 of 8** agents | No | **0%**. [Detail](/docs/cost/what-does-not-work#prompt-caching-does-not-engage) |
| Lower `max_tokens` | Failed all three of its own criteria | No | **0%**, and it destroys analyses. [Detail](/docs/cost/what-does-not-work#max_tokens-failed-all-three-criteria) |

## Lever 1: `global.*` instead of `us.*` — exactly −9.09% [#lever-1-global-instead-of-us--exactly-909]

`us.*` and `global.*` cross-region inference profiles address the **same weights** through the **same API** with the same behaviour. `us.*` bills at exactly **1.10x** `global.*` on **every** rate category — input, output, cache read, cache write. So choosing `global.*` saves 1 − 1/1.10 = **9.0909…%**.

Verified on the projected per-adjudication cost, both prefixes, same tokens, same date:

| Prefix | Specialists (8 Claude calls) | Synthesizer | Total | Saving |
|---|---:|---:|---:|---:|
| `global.*` | **$0.11412** | $0.01063 | **$0.12475** | — |
| `us.*` | $0.12553 | $0.01063 | $0.13616 | — |
| Delta | **−9.09% exactly** | — (no prefix exists on mantle) | **−8.38% blended** | |

Note which figure is which. **The 9.09% applies to the Claude specialist calls only.** The synthesizer is on `bedrock-mantle`, which has no `global.*` / `us.*` prefix and no cross-region inference — the model id is bare and the call is in-region. So the *blended* per-adjudication saving on this nine-call pipeline is **8.38%**, and quoting 9.09% as the end-to-end figure would be slightly wrong. Both are computable from the code; neither is rounded here.

`REGIONAL_MULTIPLIER = 1.10` lives next to the prefix in `agents/models.py`, and `agents/pricing.py` reads the multiplier from the **prefix carried by the model id** — `prefix_of(model_id)` — rather than from the process-wide default. So a model id built with an explicit prefix, or read back from a live response, is still priced correctly. Pricing a `us.*` call at global rates would under-report by 9.09% silently.

That prefix is env-overridable (`BEDROCK_MODEL_PREFIX`), because a customer with a data-residency requirement needs `us.*`. An unknown value **raises**: a silently-accepted typo would route every agent to a model id that does not exist and produce cost math that cannot be trusted.

## Lever 2: batch inference — −50% with a real exclusion list [#lever-2-batch-inference--50-with-a-real-exclusion-list]

Batch inference is half price where Bedrock offers it. It does **not** offer it everywhere, and the exclusions are exactly the models this pipeline uses most.

| Model | Batch offered | Consequence for this pipeline |
|---|---|---|
| Claude Opus 5 | **Yes** | No agent runs on Opus any more |
| Claude Sonnet 4.6 | **Yes** | The source system's model, not ours |
| Claude Haiku 4.5 | **Yes** | `dealer` and `straw` — the two cheapest agents |
| **Claude Sonnet 5** | **No** | **Six of eight specialists** |
| Claude Opus 4.8 | No | |
| Claude Opus 4.7 / Fable 5 | No | |
| GPT-5.6 (any variant) | No | The synthesizer |

Priced on the recorded per-agent tokens, taking batch wherever it is offered and on-demand everywhere else:

| | Projected $/adjudication |
|---|---:|
| All on-demand | **$0.12475** |
| Batch where offered (`dealer` + `straw` only) | **$0.12028** |
| **Saving** | **−3.58%** |

Because the two batch-eligible agents are also the two cheapest, a −50% discount on them is worth 3.58% of the bill. **A bulk-underwriting plan assuming −50% end-to-end is wrong by an order of magnitude on this assignment.** `rates_for(..., batch=True)` raises `UnsupportedBatchError` for a model with no batch price rather than silently applying the discount.

Two further constraints. **Batch and prompt caching are mutually exclusive** on the same request (`BATCH_AND_CACHING_ARE_EXCLUSIVE = True`), which costs nothing here because [prompt caching does not engage anyway](/docs/cost/what-does-not-work#prompt-caching-does-not-engage). And **batch is not real-time** — an offline queue, so it does not apply to the forward-flow underwriting path the customer's sub-minute target describes. It applies to a **backfill**, and the customer has a very specific one: their own reported figure is **4,500 applications taking over 48 hours**. That is where batch is worth having, and it is a different workload from the demo.

If the September rate change forces a re-look, note the shape it creates: **Sonnet 4.6 at $3/$15 with batch is $1.50/$7.50, cheaper than post-promotional Sonnet 5 at $3/$15 on-demand.** For a backfill the *older* model becomes the cheaper choice. That is arithmetic on the rate card, not a measurement, and no quality comparison of Sonnet 4.6 against Sonnet 5 exists in this repo.

## Lever 3: precomputed signals remove per-application Analyst calls

Largest structural saving, and the one that is not a Bedrock rate at all. The port keeps the customer's own two-layer separation: governed signals are generated **first** (`signal_layer/`), then handed to the agents for interpretation (`agents/`). The same agent never both queries and investigates.

| Per application | Incumbent path | Here |
|---|---|---|
| Cortex Analyst messages | **8** | **0** |
| Warehouse executions | **8** | **0** |
| LLM calls | 9 | 9 |

**This is a structural claim, not a priced one.** No dollar figure is put on the removed Analyst calls or warehouse executions anywhere on this site, because doing so would require the customer's Snowflake credit rate, their warehouse size, and their Analyst message pricing — none of which we have. What is claimable is the **count**. Their leadership often finds the count more persuasive than a latency number, precisely because they know what a warehouse-second costs and we do not.

A **latency** argument attaches to the same change, and it is why the architecture looks like this at all: a published production decomposition of a Cortex Agent call attributes **~27 s of a 55 s total** to Cortex Analyst SQL generation alone. For a fixed set of fraud signal groups the queries are known at design time, so regenerating them per application buys nothing. That figure is **not our measurement** — it is a published third-party decomposition, labelled as such wherever it appears. See `docs/semantic-layer-mcp.md` and [the semantic layer](/docs/platform/semantic-layer).

## GPT-5.6 cache-write tokens bill at 1.25x input [#gpt-56-cache-write-tokens-bill-at-125x-input]

Not a lever — a **correction**, and the largest single mis-pricing found in this engagement.

GPT-5.6 turns implicit caching on by default. A first call against a large prompt reports most of its input as `cacheWriteInputTokens`, and **cache-write bills at 1.25x the uncached input rate** (a 30-minute cache).

| Measured Luna synthesis call | Value |
|---|---:|
| `cacheWriteInputTokens` | **6,740** |
| Cost of that term alone | **$0.00927** |
| Total cost of the call | **$0.01499** |
| **Share of the bill the term represents** | **62%** |

Dropping the term under-reported that call by 62%. `agents/mantle.py:CACHE_WRITE_MULTIPLIER` prices it, with a regression test. Note the variant asymmetry: **GPT-5.4 and GPT-5.5 cache automatically with NO write charge**, so their multiplier is **0.0**. A single hard-coded 1.25x across the GPT family would over-report those two.

Synthesis rows from the pipeline itself show why this is not an edge case:

| Synthesizer token class, mean per call over 42 runs | Value |
|---|---:|
| Input | **2.0** |
| Output | 715.9 |
| Cache read | 0.0 |
| **Cache write** | **4,300.2** |

**Two** input tokens and **4,300** cache-write tokens. Essentially the entire ~31K-character prompt lands in the cache-write class on every application, because every application's prompt is new. Pricing the synthesizer without that term would report it as almost free.

## Where a cost figure is allowed to come from

| Source | What it may publish |
|---|---|
| `evals/bench.py` on a live run | Measured cost per adjudication, with n |
| `agents/pricing.py:cost_usd` on a real usage dict | The cost of one measured call |
| `agents/models.py:projected_cost_per_adjudication` | A **PROJECTION**, labelled as one in every return value |
| `agents/pricing.py:compare_tiered_vs_uniform` | A saving, **decomposed** into `structural_saving_usd` + `model_saving_usd` |
| Anything else | Nothing |

`cost_usd_or_none` exists so a caller with unknown usage renders an em dash rather than a fabricated figure. `agents/mantle.py:cost_usd` returns `None` for a missing usage dict for the same reason, and `rates_for` **raises** for an unpriced model id, with the message `no verified rate card for {model_id}; refusing to price it.`

## Measured cost this all sits under

For the avoidance of doubt about which number is a measurement:

| | Value | Status |
|---|---|---|
| Cost per adjudication, prior assignment | **$0.1177 min / $0.1440 p50 / $0.2536 max** (n=41 priced runs) | **MEASURED** |
| Cost per adjudication, current assignment | $0.12475 | **PROJECTION** |
| Total measured Bedrock spend for the benchmark | **$6.46592** (42 runs, 336 specialist calls) | MEASURED |

Spread across those 41 runs is **$0.1359**, and because rates are fixed per model, **token volume is the only driver**. Between the cheapest and the most expensive run, specialist *input* tokens differ by 7% and specialist *output* tokens differ by **3.35x** (4,098 vs 13,735). Cost variance on this workload is an output-length story. [Measured results](/docs/measured-results#cost-per-adjudication).

## Still unknown

**Whether any of this is cheaper than the incumbent.** That is not a measurement gap on our side — it needs one number from the customer, and at the two ends of a plausible range the same architecture gives opposite answers. Also unmeasured: the end-to-end cost of the *current* assignment (a projection until `evals.bench --pipeline --repetitions 3` runs), and anything under concurrency, since applications were benchmarked one at a time.

# PATCH-2026-08-25 — retry Bedrock's transient 5xx, not just the 429

Shareable. Written to be pasted into Kiro (or any coding agent) as an implementation task.
Everything asserted below was read out of the installed wheels or measured in a run; the
"Evidence" section says which, and the two places where a number depends on your
configuration are called out rather than averaged over.

---

## The symptom, in your own errors

```
(1) An error occurred (ThrottlingException) when calling the ConverseStream operation
    (reached max retries: 2): Too many tokens, please wait before trying again.

(2) An error occurred (ServiceUnavailableException) when calling the ConverseStream operation
    (reached max retries: 2): Bedrock is unable to process your request.
```

Error (2) appeared after `max_tokens` was lowered, and CloudWatch moved from **Throttles** to
**Errors**. That progression is real and it is good news: (1) is your account's token quota
refusing the request, (2) is Regional capacity shedding *after* you cleared that gate. The
bottleneck moved back one layer.

What is not obvious is that **your retry budget collapsed at the same moment**, silently, and
that is why a slow 45-minute ramp still failed at 35 parallel requests. A 429 and a 503 travel
the same code path and get very different numbers of attempts.

---

## Step 0 — decide which of two patches you need

This changes the whole answer, so establish it first.

```bash
# Does the failing service import Strands?
grep -rn "strands" --include=pyproject.toml --include=requirements.txt --include='*.py' . | head
```

- **Strands Agents SDK** in the call path → apply **Patch A**. The gap is in the SDK's retry
  strategy and `Config(retries=...)` will not close it.
- **boto3 / botocore directly** (`client.converse_stream(...)`) → apply **Patch B**. There is no
  Strands layer, and the lever is botocore's own retry config.

Both errors above are `botocore.exceptions.ClientError`, and the `(reached max retries: 2)` text
is botocore's, so **the message alone does not tell you which case you are in.** It is printed
identically whether or not Strands is above it.

## Root cause (Patch A — Strands)

Verified against `strands-agents==1.50.2`, source quoted, not recalled.

`strands/event_loop/_retry.py:61` — the entire retry predicate:

```python
def is_retryable(self, exception: Exception) -> bool:
    return isinstance(exception, ModelThrottledException)
```

`strands/models/bedrock.py:1044` — the only place that produces a `ModelThrottledException`:

```python
except ClientError as e:
    error_message = str(e)
    if (
        e.response["Error"]["Code"] == "ThrottlingException"
        or e.response["Error"]["Code"] == "throttlingException"
    ):
        raise ModelThrottledException(error_message) from e
    ...          # context-window overflow, then two add_exception_note() cases
    raise e      # <-- everything else, including every 5xx, leaves as a raw ClientError
```

There is **no 5xx branch**. So:

| | promoted? | `is_retryable`? | Strands retries |
|---|---|---|---|
| `ThrottlingException` (429) | yes | True | 3 |
| `ServiceUnavailableException` (503) | no | **False** | **0** |
| `InternalServerException` (500) | no | **False** | **0** |

Measured end to end, injecting the fault at the botocore layer and counting attempts
(`tests/test_retry_transient.py`), 503 twice then success:

```
stock strands  -> ClientError after 1 attempt
patched        -> OK after 3 attempts
```

### What that costs, concretely

Per-request HTTP attempts, Strands `max_attempts=4` over botocore's default 3:

| error | Strands attempts | × botocore attempts | total HTTP attempts | Strands-contributed wait |
|---|---|---|---|---|
| 429 | 4 | 3 | **12** | 7s (`[1, 2, 4]`) |
| 503, before patch | 1 | 3 | **3** | **0s** |
| 503, after patch | 4 | 3 | 12 | 7s |

**Two numbers here depend on your configuration — do not quote them without checking.**

botocore's own backoff has two code paths, gated by `NEW_RETRIES_ENABLED` in
`botocore/configprovider.py`, which reads the env var `AWS_NEW_RETRIES_2026` and otherwise
defaults to **False** in public botocore. Measured on botocore 1.43.80:

| branch | condition | 429 backoff | 503 backoff |
|---|---|---|---|
| active by default | flag unset/false | ~1.5s mean (3.0s max) | ~1.5s mean — **same** |
| the other one | `AWS_NEW_RETRIES_2026=true` | ~1.5s mean | **~75ms mean** |

So on a default install the 503's *waiting* is comparable to the 429's; what it loses is
**attempts** (12 → 3). Only with that flag set does the wait itself collapse by ~20x as well.
Either way the fix is the same, and either way the shed request gets one-quarter the chances.

Regional shedding passes in seconds. Three attempts inside ~1.5s does not outlast it; twelve
attempts across ~8.5s frequently does. That is the whole bug.

## Patch A — Strands

`is_retryable` is the SDK's own documented extension point. From the `ModelRetryStrategy`
docstring:

> Subclass and override `is_retryable` to expand or narrow the set of retryable exceptions
> without reimplementing the rest of the retry policy.

**Do not override `_handle_after_model_call`.** It owns the backoff ladder, the `max_attempts`
test and the reset on `AfterInvocationEvent`. Overriding it is how a retry patch silently
changes your latency budget.

```python
from typing import Any, Final

# Tune to your own SLA. These are ours: ladder [1, 2, 4]s, 7s worst case.
RETRY_MAX_ATTEMPTS: Final[int] = 4
RETRY_INITIAL_DELAY_S: Final[int] = 1
RETRY_MAX_DELAY_S: Final[int] = 8

#: Membership is keyed on httpStatusCode in botocore's own service model
#: (data/bedrock-runtime/2023-09-30/service-2.json.gz), not on the spelling:
#:   in  -- ServiceUnavailableException (503), InternalServerException (500), and
#:          ModelNotReadyException (429, which the model itself flags retryable).
#:   out -- ModelErrorException / ModelStreamErrorException (424) are model-level
#:          failures a retry reproduces; ModelTimeoutException (408) is excluded on
#:          the SLA, since the request already spent its wall clock once.
#: Compared lower-cased: Bedrock spells request-time codes upper-camel and stream-time
#: codes lower-camel, which is why bedrock.py above has to test "throttlingException" twice.
RETRYABLE_TRANSIENT_ERROR_CODES: Final[frozenset[str]] = frozenset({
    "serviceunavailableexception",
    "internalserverexception",
    "modelnotreadyexception",
})


def transient_error_code(exception: BaseException) -> str | None:
    """The Bedrock error code if this is a retryable transient fault, else None.

    botocore.exceptions.EventStreamError needs no branch of its own: it subclasses
    ClientError and carries the same response['Error']['Code']. That one fact covers
    both failure shapes -- ClientError when converse_stream is refused outright, and
    EventStreamError when the stream opened and then broke mid-flight, which botocore's
    own retry layer cannot see at all because the HTTP call already succeeded.

    .get() chains rather than response["Error"]["Code"]: this runs INSIDE a retry hook,
    and a KeyError here would replace the real Bedrock failure at the top of the
    traceback -- turning a capacity incident into a phantom bug in this function.
    """
    from botocore.exceptions import ClientError

    if not isinstance(exception, ClientError):
        return None
    code = (exception.response or {}).get("Error", {}).get("Code")
    if not isinstance(code, str):
        return None
    return code if code.lower() in RETRYABLE_TRANSIENT_ERROR_CODES else None


def build_retry_strategy() -> Any:
    """Retry throttles AND transient Bedrock faults, on one bounded budget."""
    from strands.agent import ModelRetryStrategy

    class _ThrottleAndTransientRetryStrategy(ModelRetryStrategy):
        def is_retryable(self, exception: Exception) -> bool:
            # super() first: ModelThrottledException is the promoted form of a 429, so
            # this keeps existing throttle behaviour byte for byte.
            if super().is_retryable(exception):
                return True
            return transient_error_code(exception) is not None

    return _ThrottleAndTransientRetryStrategy(
        max_attempts=RETRY_MAX_ATTEMPTS,
        initial_delay=RETRY_INITIAL_DELAY_S,
        max_delay=RETRY_MAX_DELAY_S,
    )
```

Then pass `retry_strategy=build_retry_strategy()` everywhere you construct an `Agent`, and
build **a fresh strategy per Agent** — it carries per-invocation state (`_current_attempt`).

### Do not widen the 429 budget while you are in here

This is the part that gets applied backwards. A throttle means your token reservation was
*refused*, so a retry re-enters the same auction and competes with the requests still holding
reservations; more retries make throttling worse. A 503 touches no quota accounting at all, so a
retry is simply a second chance at a queue that drains in seconds. **Retry policy has to be keyed
on the error code — one global answer is wrong for one of the two.** The patch above is additive
on other codes only; `super().is_retryable` is called first precisely so the 429 path is untouched.

### On the shared budget

`ModelRetryStrategy` keeps a single `_current_attempt` used for both the delay and the
`max_attempts` test, so per-code budgets would mean overriding `_handle_after_model_call` — the
thing the docstring tells you not to reimplement — and would double the worst case. We kept one
shared, capped budget deliberately. If 7s proves too short against real shedding, **measure that
and then change it**; do not pick a bigger number in advance.

## Patch B — raw boto3 / botocore

If Strands is not in the path, the 503 *is* already retried — botocore classifies HTTP 500/502/503/504
as transient — but only twice, because `DEFAULT_MAX_ATTEMPTS = 3`.

```python
from botocore.config import Config

bedrock = boto3.client(
    "bedrock-runtime",
    config=Config(
        retries={"max_attempts": 8, "mode": "adaptive"},   # TOTAL attempts, not retries
        read_timeout=120,
        connect_timeout=10,
        max_pool_connections=32,   # botocore's default of 10 will cap your parallelism
    ),
)
```

Notes that matter:

- `max_attempts` is **total attempts**, so `8` means 7 retries.
- `mode="adaptive"` adds client-side rate limiting on top of `standard`. Worth having, but it is
  not what fixes this — `max_attempts` is.
- **botocore cannot retry a mid-stream failure.** Once `converse_stream` returns and you begin
  iterating `response["stream"]`, a fault arrives as `EventStreamError` and botocore is no longer
  involved; `max_attempts=10` will not help. You need your own retry around the *stream
  consumption*, not just the call. Treat a partially-consumed stream as a failed request and
  re-issue it.

## Tests to add

Classification alone is not enough — assert the retry actually *fires*. Replace the client with a
stub that fails N times then succeeds, and count attempts. No AWS calls, no spend.

```python
class _FlakyClient:
    def __init__(self, fail_times, code):
        self.fail_times, self.code, self.calls = fail_times, code, 0
        self.meta = type("_Meta", (), {"region_name": "us-west-2"})()

    def converse_stream(self, **_kwargs):
        self.calls += 1
        if self.calls > self.fail_times:
            return _ok_stream()          # a minimal valid ConverseStream event sequence
        raise ClientError({"Error": {"Code": self.code, "Message": "synthetic"}}, "ConverseStream")
```

Cover at minimum:

1. Each transient code is retried and the call **recovers** — assert attempt count, not a boolean.
2. Both spellings of each code (`ServiceUnavailableException` and `serviceUnavailableException`).
3. A `ThrottlingException` behaves **identically** to before the patch — same attempts, same ladder.
4. An `EventStreamError` raised mid-stream is retried.
5. `ValidationException` / `AccessDeniedException` are **not** retried (1 attempt, no sleep).
6. The budget is bounded: a Region that stays down stops at `max_attempts` and re-raises the real
   error, so the caller sees Bedrock's failure and not a timeout.
7. **A canary that pins the SDK gap**: assert stock `ModelRetryStrategy` still returns
   `is_retryable(503) is False`. If a future SDK closes the gap, that test fails — and the correct
   response is to **delete the subclass**, not relax the test. Without it the subclass quietly
   outlives its reason to exist.

Stub `asyncio.sleep` inside `strands.event_loop._retry` and *record* the delays rather than
waiting them out. The tests stay fast and additionally assert the real ladder the real loop chose.

Then **mutation-test the tests**: revert the strategy to bare `ModelRetryStrategy`, drop a code
from the set, remove the `.lower()`, swap the `.get()` chain for `["Error"]["Code"]`. Each should
turn something red. A retry test that passes against a reverted patch is worse than no test.

## What this does NOT fix

State this plainly to anyone who reads the patch, because a retry fix invites the assumption that
the capacity problem is solved.

1. **It does not create capacity.** Retries help when shedding is brief. A Region under sustained
   pressure will exhaust any budget, and 12 attempts that all fail cost more wall clock than 3.
2. **It does not reduce quota consumption.** The levers there are separate and larger:
   `max_tokens` (debited up front at `input + max_tokens` and throttled on that *reservation*, not
   on what gets generated) and prompt caching (`CacheReadInputTokens` does not count toward quota
   at all).
3. **It does not remove the need to ramp.** Bedrock's scheduling favours steady-state traffic;
   step up and hold rather than jumping to target.
4. **Daily caps are unaffected and non-adjustable.** A tokens-per-day ceiling is not something a
   TPM increase or a retry policy moves.
5. **A mid-stream failure may re-deliver a prefix.** Retrying re-runs a call whose partial deltas
   already reached your callback. Harmless if you keep only the final text; visible if you render
   token-by-token. Buffer, or de-duplicate on retry.
